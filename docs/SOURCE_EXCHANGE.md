# Scoped lead source exchange API

The /api/integrations/v1 routes provide revocable-key, workspace- and tenant-scoped operations. They do not perform lead research or send customer messages. No key, writer grant or ownership transition is created by adding a route.

POST operations requires operationId, clientId, tenantId, writerEpoch, action, entityType lead, targetId, expectedRevision, patch and evidence. The Idempotency-Key header equals operationId; original bytes are immutable. A revocable brand-scoped API key identifies the principal. Legacy shared keys and browser sessions cannot authorize this boundary. The active writer grant explicitly names workspace, tenant and fields, and the ownership epoch must match.

The Mongo transaction validates the application's lead contract and forbidden terms, preserves existing user-owned pipeline fields, normalizes contacts and field verifications, applies the accepted effect and stores its operation result atomically. Creates use the application's neutral ICE defaults and start in DISCOVERED. Machine patch fields are restricted to research content and controlled taxonomy inputs. Classification and merge keys remain server-derived. Content revisions include substantive source values and exclude working timestamps. Private operation receipts, grants, ownership and uniqueness reservations live in integration_operations, integration_writer_grants, integration_ownership and integration_identities.

Every changed top-level research field requires source evidence. Contact evidence binds to the existing contactKey helper's identity, never an array index. Newly changed contact fields require attached provenance; those entries persist on their contact object. Only independently checked public-source verification methods are accepted. An operation cannot fabricate an admin, user, phone-call or email verification. Evidence URLs are bounded HTTPS references and never trigger a receiver-side fetch.

GET operations by UUID, with the explicit brand query, returns the same principal's immutable result. Resolve an unknown HTTP outcome through this exact lookup; do not create a replacement write under a new identity. POST deliveries/lookup requires explicit clientId, tenantId, exact leadIds and granted fieldPaths. It maps id and _id explicitly, returns missing IDs and fields, checks only the requested workspace/tenant and includes persisted provenance. Private leads always have publication kind private-lead and isPublished false. Readback and raw contact data never belong in the public exchange dashboard.

The implementation has focused contract tests and an isolated loopback Mongo verifier. Production enrollment is separate: review the principal/field/tenant matrix, establish transaction-capable storage, reconcile old uncertainty, release the application and verify each enrolled workspace through normal scheduled processing. Keep unresolved receipts and reservations through rollback. Never restore old operation state over newer writes or clear a hold to force progress. No enrichment batch or customer content is created as a development check.
