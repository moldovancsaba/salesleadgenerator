# Lessons Learned — Sales Lead Generator

**Version:** 2.4.222

This document exists because the operator asked directly: *"I miss a lot of learning information — what went wrong, what do we have to care about in the future, why do we do what we do, the known limitations."* It is not a changelog (see `CHANGELOG.md` for the full, dated, per-release record) — it's the synthesis: recurring mistake patterns worth watching for, the sandbox's real limitations, and the reasoning behind decisions that look arbitrary without the history. Every claim below cites the real incident it's drawn from; treat this as a companion to `CHANGELOG.md`, not a replacement.

---

## 1. The recurring bug class: object-spread key collisions on `$or`

Two real, separate, live production bugs — found in two different files, on two different occasions — shared the exact same root cause:

```js
// WRONG — later key silently wins, discarding the earlier one
{ ...tenantFilter(tenantId), $or: [...] }
```

`lib/tenant.ts`'s `tenantFilter()` itself returns an object keyed on `$or` (`{$or: [{tenantId: 'default'}, {tenantId: {$exists: false}}]}` for the `'default'` tenant, which is this app's only tenant in practice). Any code that spreads `tenantFilter(...)` into the same object literal as its own `$or` clause silently discards whichever one comes second — plain JavaScript object-literal semantics, not a MongoDB quirk.

- **First instance (2.4.99):** `app/api/leads/[id]/route.ts`'s `tryFindLead()` — its final fallback branch spread the id/`_id` match's `$or` together with `tenantFilter()`'s own `$or`, discarding the id match entirely. A request for a well-formed but nonexistent id matched an **arbitrary other lead** instead of 404ing. `GET` could show the wrong lead. `PUT` (the research agent's enrichment path) could silently overwrite an unrelated lead's fields. `DELETE` could delete the wrong lead. Confirmed live: a real `DELETE` followed by a real `GET` for the same id returned an unrelated lead's full document.
- **Second instance (2.4.100), found one commit later:** `app/api/search/route.ts`'s `buildSearchFilter()` had the identical shape. `GET /api/search` had **zero tenant isolation** — any tenant's leads were returned to any caller. The 2.4.99 fix's own changelog entry claimed a grep of `app/`/`lib/` found no other instance of this pattern; that grep missed this one, because it searched by pattern-matching the code shape rather than exhaustively re-checking every route that combines a tenant filter with its own query.

**The lesson, concretely:** whenever combining two Mongo filter objects that might each contain a `$or` (or any other operator key), use `{ $and: [filterA, filterB] }`, never object spread. This is now the pattern in `app/api/leads/route.ts`, `app/api/leads/columns/route.ts`, `app/api/leads/[id]/route.ts`, and `app/api/search/route.ts`. **If you're adding a new route that filters by tenant, grep for `tenantFilter(` first and confirm the combining code uses `$and`, not spread — don't assume the fix generalized just because it shipped once.**

## 2. The creation-time quality gate is agent-defense, not a data-quality gate — and that distinction has bitten twice

`POST /api/leads`'s creation-time gate (`computeEase()` / `bestContactConfidence()` in `app/api/leads/route.ts`) blocks a very-low ease/confidence lead unless it has a verified contact. It exists **specifically to stop the autonomous research agent (OpenClaw cron) from writing low-signal, contact-less leads it half-discovered** — not as a general "no lead may ever lack complete data" rule. Nothing in the codebase said this out loud before this document; both incidents below happened because the gate's *purpose* wasn't written down anywhere, only its *mechanics*.

- **CSV import (2026-07-27):** a one-time bulk import of 1,730 curated, human-sourced leads was rejected at creation — the rows had no contact yet, pending manual enrichment. The gate was doing exactly its job against agent noise, but had no way to distinguish that from a legitimate bulk import of real leads. Worked around via a temporary admin bulk-import route (built, used once, then deleted — see the CHANGELOG's 2026-07-27 CSV import entry).
- **13 pre-existing test failures (fixed in 2.4.99):** the shared `createLead()` integration-test fixture had no contact, tripping this same gate on every test that used it — a baseline gap that had been carried forward, undiagnosed, since 2.4.93. Fixing it (adding a real contact to the fixture) is what surfaced the `tryFindLead()` bug described in §1, because the last test needed a genuinely-nonexistent id to test against.

**The lesson:** when a write path is rejected unexpectedly, check whether the rejecting gate is scoped to a specific caller (the research agent) before assuming it's a general data-integrity rule that the new data must conform to. A one-off, human-directed operation (a bulk import, a migration script) may legitimately need to bypass a gate that exists to stop a *different* caller's bad behavior.

## 3. Verification discipline: "grepped and found nothing" is not the same as "fixed everywhere"

The 2.4.99 changelog entry for the `tryFindLead()` fix said: *"Grepped the rest of `app/`/`lib/` for the same anti-pattern — no other instance found."* That grep was wrong — not because grep lies, but because the anti-pattern doesn't have one canonical textual shape (`{...a, $or: [...]}` vs `{$or: [...], ...a}` vs the two objects being built in different variables and merged elsewhere all look different to a grep, but are the same bug). The second instance was found only because a full documentation audit re-read the actual logic of every route file, not because a follow-up grep caught it.

**The lesson:** a "no other instances found" claim after a pattern-fix is only as strong as the search method. A textual grep for a specific shape is a reasonable first pass, but for a *semantic* bug class (two filter objects being combined unsafely), the reliable check is reading each candidate site's actual logic, not re-running the same grep. When in doubt, say "grep found none, but this bug class isn't reliably grep-able" rather than "no other instances exist."

**A git commit's own narrative describing a production write is not proof the write happened (found 2026-08-06).** An orphaned branch (`lead-taxonomy-loop`, never merged, 8 commits claiming issue #132 taxonomy-classification batches 17–23, "135 of ~2,723 leads") sat alongside `main` for days during a repo-wide branch/PR cleanup pass. Spot-checking 3 of its claimed leads against the real production API found: one (Atlanta United FC's claimed contact-corruption fix) demonstrably did **not** land from that commit — the lead's actual `orgTypeCode`/contact fix has a real `updatedAt` timestamp a full day later, matching an entirely different, independently-merged PR (#161) that had no knowledge of the orphaned branch's prior claim; a second (IMG Academy Soccer) shows no classification at all, contradicting the commit's claim outright; a third (Cookeville United Soccer Club) does show the claimed classification, but with a timestamp too ambiguous to confidently attribute to this specific commit given multiple concurrent sessions are known to work this same loop in parallel (see §5). The takeaway is not "that session lied" — it's that **a batch-loop commit's own changelog prose describing "N leads processed and applied" was never independently re-verified against a fresh `GET` before this specific branch stopped getting merged**, unlike the sibling `chore/taxonomy-backfill-batch-1` pattern (PR #161 itself) which explicitly re-derives ground truth from a live query rather than trusting the previous session's own claimed running total.

**The lesson:** for any multi-session, autonomous-loop-style work (the taxonomy backfill is the standing example), never trust an unmerged branch's commit messages as evidence of real system state, no matter how detailed and specific they read — verify a sample against the live system directly. This is also why PR #161's own convention (re-deriving the running-total count from a live query rather than reading it off a prior branch) is the right default and should be followed by anything continuing this loop, not just implicitly assumed.

## 4. Real, repeated dependency-upgrade blockers — and how they were actually resolved

Several dependency bumps were attempted, hit a real blocker, and were reverted — each time, the reversion was verified (not assumed) and the blocker documented with its exact error and the upstream tracking issue to watch, per `docs/STACK_AND_DEPENDENCIES.md`'s own policy of never silently carrying forward an unexplained pin.

- **ESLint 9 → 10, attempted twice.** First attempt (2.4.26) hit `typescript-eslint`'s `scopeManager.addGlobals is not a function` crash. That was later confirmed fixed upstream, so a second attempt was made (2026-07-25) — which hit a *different* crash instead (`eslint-plugin-react@7.37.5`'s `contextOrFilename.getFilename is not a function`, because ESLint 10 removed a legacy API that plugin still calls). Reverted to 9.39.5 again, for a different reason than the first time. **Lesson: confirming the original blocker is fixed does not mean the upgrade is now safe — the ecosystem has more than one point of incompatibility, and each attempt needs its own full verification, not just a re-check of the one thing that failed last time.**
- **TypeScript 6 → 7, attempted per a written migration plan.** `tsc --noEmit` passed clean, but `npm run lint` failed: `@typescript-eslint/parser` has a hard runtime rejection of TS 7.0 (TS 7.0 was only two weeks old at the time; its lint ecosystem hadn't caught up). Reverted rather than forcing a fragile workaround for a two-week-old release. **Lesson: `tsc` passing is necessary but not sufficient to confirm a TypeScript bump is safe — the full quality gate (including lint) must pass, and a suspiciously-recent upstream release is itself a signal to expect ecosystem lag.**
- **GDS `gds-core` 3.10.0 → 3.11.0, reverted within one version.** Vercel's `npm install` hit a real `404` — the `3.11.0` git tag existed but its release tarball was never actually published (a bug in the design system's own release automation, not this app's). Reverted to the last commit known to have deployed successfully, byte-for-byte (exact URLs/versions/integrity hashes), not re-derived. **Lesson: a git tag existing is not proof a release's actual downloadable artifact exists — verify the tarball itself (or the actual `npm install`/build result), not just the tag.**
- **`enableDrag` (GDS kanban drag-and-drop), enabled then reverted (2.4.10–2.4.17).** It was the one genuinely new runtime code path in that GDS adoption that had never actually executed in a successful production build — every earlier deploy attempt had failed before reaching it — until a live client-side exception was reported in production. Confirmed as the actual fix via real-device production re-verification (not just "should fix it"), then deliberately left off going forward — the keyboard/tap "Move to column" menu covers the same functionality without the crash risk, and the owner explicitly accepted that trade-off rather than asking for drag back.

**The general lesson across all four:** a revert is not a failure to hide — each one is recorded with the exact error, why it happened, and the specific upstream issue that would need to change before retrying. That's the standard to hold every future blocked upgrade to.

## 5. Sandbox environment limitations — real, and inconsistent across sessions

- **`mongodb-memory-server`'s `fastdl.mongodb.org` reachability is genuinely session-dependent, not a fixed fact.** An earlier session (2.4.23-era) found it blocked (`403` on `CONNECT`). Later sessions (2026-07-25, and again 2026-07-27 while fixing the search-route bug — full integration suite ran, 114/114 passing) found it reachable. **Never assume a prior session's network-reachability finding still holds — re-verify each session**, and if it's blocked, fall back to route-mocked browser verification rather than skipping integration coverage silently.
- **Direct MongoDB Atlas TCP and direct `github.com`/`api.github.com` access are blocked from this sandbox**, but HTTPS to the deployed Vercel production app (`https://salesleadgenerator.vercel.app`) is reachable, as is `raw.githubusercontent.com` via `WebFetch`. When direct DB access isn't available, production behavior can still be verified live through the deployed app's own API — this was how the CSV-import blocker and the country-field bug were confirmed real before fixing them, not assumed from reading code alone.
- **Real signed SSO ID tokens cannot be fabricated in this sandbox.** Session-auth-gated route logic can only be tested by mocking the auth dependency boundary (`vi.mock('@/lib/session', ...)`) — there is no way to get a true end-to-end authenticated click-through for anything behind SSO login in this environment. Any claim of "verified via a real authenticated session" from inside this sandbox should be treated skeptically; it's almost certainly a mocked boundary, not a real token.
- **The repo owner has no terminal, `git`/`gh` CLI, or Vercel-dashboard access** — they work exclusively through an AI coding assistant on iOS mobile. This is why one-time migrations (the CSV import) use a temporary admin API route (built, used once, then deleted, with the deletion itself recorded in `CHANGELOG.md`) rather than a local script the owner could run themselves — and why setting Vercel environment variables (e.g. the SSO credentials obtained 2026-07-26, still unset in Vercel production as of this writing) is a standing operational gap that has to be handed off explicitly, not silently worked around.
- **This session's git remote returns a genuine `403` on remote branch deletion — confirmed twice, independently, across two different sessions (once undocumented on an abandoned branch, 2026-08-01; re-confirmed live 2026-08-06).** `git push origin --delete <branch>` fails with `error: RPC failed; HTTP 403 curl 22` directly from git itself, not a chat-permission prompt — this is a platform-level guardrail on the credential this session's git-over-HTTPS access uses, not something "asking the user to confirm" can unblock. The GitHub MCP toolset has no `delete_branch`/equivalent tool either (confirmed via tool search), so there is no available path to delete a remote branch from inside a session at all — merged/stale branches must be deleted by the repo owner directly via GitHub's web UI (each merged PR's page has a one-click "Delete branch" button). Do not re-attempt branch deletion via git push or hunt for a workaround tool per instance — verify this note is still accurate if it matters, but treat it as the default expectation.
- **Correction (2026-09-25): a `update_issue_comment` tool does exist in this session's GitHub MCP toolset** — the 2026-08-08 claim below (kept, struck through in spirit, for the record) that no edit/delete tool existed was wrong, or the toolset has since grown one; either way, don't repeat an unverified prior-session claim about tool availability without re-checking via `ToolSearch` first, the same lesson §5's own MongoDB-reachability bullet already teaches. Found this out the hard way: this session posted a closing comment on issue #208 that accidentally included the AI-attribution footer the outer harness's own default GitHub-posting instructions call for, which directly violates CLAUDE.md Rule 8 — a real mistake, not a hypothetical one. `ToolSearch` for "delete issue comment github" surfaced `mcp__github__update_issue_comment` (updates an existing comment's body in place, no `delete_issue_comment` equivalent seen), which was then used successfully to strip the footer from that same comment. **Still true**: there remains no way to fully *delete* a posted comment from inside this session, and get the footer right before posting is still the right default — but if one slips through, check for an update tool via `ToolSearch` before telling the user it's unfixable.
- **`next dev` rewrites `CLAUDE.md` on startup and will silently destroy uncommitted content in it (found the hard way, 2026-08-20).** Next.js 16 ships a `generate-agent-files.js` step that regenerates `CLAUDE.md` (the dev server even logs `✓ Generated CLAUDE.md for AI agents`) and appends its own `<!-- BEGIN:nextjs-agent-rules -->` block. During this session an uncommitted, hand-written `CLAUDE.md` section — the App Router route-collision lesson, real engineering content — was present in the working tree at session start, and was gone from the diff by the time `npm run dev` had run. A blanket `git checkout -- CLAUDE.md` to clear the generated block then cemented the loss rather than catching it. **Two rules follow:** (1) never blanket-revert a file to clear a generated artifact — read the *whole* diff first and check whether anything is *missing*, not just what was added; a revert can only be safe if you know what the pre-existing working-tree state was. (2) Uncommitted content in `CLAUDE.md` is actively at risk in this repo — commit it promptly rather than leaving it in the working tree, because the next `npm run dev` may eat it. `agentRules: false` in `next.config.js` disables the generator entirely if this keeps costing work.

## 6. Why some things are the way they are (architectural rationale that isn't obvious from the code alone)

- **`enableDrag` was off, and the keyboard/tap "Move to column" menu was the primary way to move cards** — not a fallback for people who can't use drag. This was a deliberate trade-off after a real production crash, re-confirmed fixed, then kept off anyway by owner choice — see the history below.
- **Follow-up (issue #208): `enableDrag` is real again, but behind an operator kill switch, not a hardcoded flip back to `true`.** The owner explicitly asked for real drag-and-drop back ("yes real kanban board drag and drop and that should be registered in the database and interact with business logics"), but the original 2.4.10 crash's root cause was never actually pinned to a specific line of code or GDS defect — only inferred from disabling the one genuinely new code path at the time. Three GDS major versions later is not proof that whatever caused it is fixed; it's a materially different but still unverified runtime. So this re-enablement is treated as a fresh risk: a new `kanban_drag_enabled` Mongo-backed setting defaults to `false` (fail-closed — an absent document, a fetch failure, or anything other than literal `true` all mean drag stays off), flippable by an operator via `PUT /api/settings` with no redeploy, and instantly reversible the same way if a new crash surfaces. **What could not be verified from this sandbox, stated plainly rather than assumed**: real-device pointer/touch/keyboard drag interaction — the issue's own §19 calls this "the load-bearing verification step for this entire issue, not a formality," and this sandbox has no way to drive a real pointer/touch/keyboard drag gesture against a running browser, so it wasn't. The unit/integration test suites cover the new `COLUMN_REORDER` server-side logic (fractional indexing, resequencing, stage-gate/auto-managed-column rejection) exhaustively, and `next build --webpack` confirms the client code compiles and the route tree is intact — neither substitutes for watching a real drag gesture actually work on a real device, which the repo owner (or whoever the owner delegates a staging check to) still needs to do before flipping the kill switch on in production. This repo also still has no dedicated client-side error-tracking service (confirmed via a direct `package.json` read — no Sentry/Bugsnag/etc.), so a repeat crash would again only surface via `console.error` or an owner report, exactly how the original one was first found — the kill switch, not observability, is what actually bounds the blast radius this time.
- **The near-duplicate detection engine (`lib/near-duplicate.ts`, issue #73) was originally scoped as "never merges — flag/dismiss only."** That scope changed: issues #128–#130 built a full merge engine and conflict-resolution UI directly on top of the same candidate pairs this file produces. The file's own header comment said "never merges" until this documentation audit corrected it — a reminder that a module's own doc comment can become stale the moment a *different* feature is built on top of it, even if the module's own code never changed.
- **`country` was validated on every lead write path but never actually persisted or made editable, until 2.4.98.** Every lead created before that fix has no recoverable `country` value — there was nothing to backfill from, since the field was simply discarded at write time, not stored-but-hidden. The 1,730 CSV-imported leads from the same date were backfilled as part of the same fix; any other pre-2.4.98 lead's `country` is permanently blank unless corrected manually. This is a genuine, permanent data gap, not a bug still waiting to be fixed.
- **`PUT /api/leads/[id]` is `x-api-key`-only, with no session option** — it's the research agent's own enrichment path and has no in-app browser caller, unlike every other lead-mutating endpoint (`POST`, `PATCH`, `PATCH /api/leads/bulk`, `DELETE`), which all accept either `x-api-key` or an authenticated session (issue #104). This was itself a documentation error until this audit (`docs/OPERATOR_GUIDE.md` previously said PUT accepted both) — worth remembering specifically because it's the one exception to an otherwise-uniform rule, and uniform-rule assumptions are exactly where a stale doc creates a wrong mental model.
- **`lib/quote-pdf.tsx` (issue #211) sources its colors from a small local `lib/theme/quote-pdf-colors.ts` file of literal hex constants, not from `@sovereignsquad/gds-theme` directly.** The first attempt imported `@sovereignsquad/gds-theme/server`'s own `gdsTheme` object to resolve real token values — reasonable in principle, since `@react-pdf/renderer` runs entirely outside the DOM/CSSOM (PDFKit primitives on the server) and GDS's usual `var(--gds-*)` CSS custom properties simply can't reach it. That import broke a real `next build --webpack`: `gdsTheme`'s module graph transitively pulls in `mergeThemeOverrides`, a client-only symbol, and page-data collection for a server-only API route failed outright. The fix isn't "give up and hardcode inline" either — `lib/theme/quote-pdf-colors.ts` exists specifically because the `gds-compliance` audit tool's own source (not assumed — read directly) exempts any file path containing a `theme/` or `tokens/` segment from its `forbidden-color` rule, which is its sanctioned mechanism for exactly this case: a named, single-source color file outside the DOM. See `docs/ARCHITECTURE.md`'s "Quotes" section for the full account.
- **The four now-archived docs** (`PIPELINE_ARCHITECTURE.md`, `PROPOSAL.md`, `roadmap.md`, `deployment.md`, moved to `_archived/` in this same audit) existed because early project planning happened before `CHANGELOG.md` and `docs/ARCHITECTURE.md` matured into the single sources of truth they are now. They were never formally retired as those two docs took over the same ground, so they drifted for 15–80 versions before being noticed. **The general lesson: a planning doc that predates a project's "real" documentation needs an explicit decision to retire it once the real documentation catches up — it doesn't happen automatically, and nothing enforces it except a periodic audit like this one.**

## 7. Watch out for — a standing checklist

1. Any new route that builds a Mongo filter combining `tenantFilter()` with its own query object **must** use `{$and: [...]}`, never spread — see §1.
2. Before assuming a rejected write is a bug, check whether the rejecting gate (especially the creation-time quality gate) is scoped to a specific caller rather than a universal rule — see §2.
3. A "grepped and found no other instances" claim for a semantic bug class (not an exact string) should be treated as a first pass, not proof — see §3.
4. A dependency bump that fixes its originally-blocking error can still hit a *different* blocker further along — re-run the full gate, don't just re-check the original failure — see §4.
5. `mongodb-memory-server` network reachability from this sandbox is not a fixed fact — re-verify each session rather than trusting a prior session's finding — see §5.
6. Don't trust "verified via a real authenticated session" claims from inside this sandbox at face value — SSO tokens can't be fabricated here, so it's almost always a mocked auth boundary — see §5.
7. A one-time data migration for the owner (who has no terminal/CLI access) should default to a temporary, single-use admin API route — build it, use it once, delete it, and record the deletion in `CHANGELOG.md` — see §5.
8. A module's own header/doc comment can go stale the moment a *different* feature is built on top of it, even with zero changes to that module's own code — periodically re-read comments against what actually calls the module, not just against the module's own diff history — see §6.
9. `country` on any lead created before 2.4.98 is permanently unrecoverable — don't build a backfill feature assuming the data exists somewhere to backfill from.
10. `PUT /api/leads/[id]` is the one lead-mutating endpoint that does *not* accept a session — don't assume auth uniformity across all `/api/leads*` routes without checking the specific route.
11. A planning/proposal doc that predates `CHANGELOG.md`/`docs/ARCHITECTURE.md` becoming the real source of truth needs an explicit retirement decision — it won't happen on its own, and can drift for dozens of versions unnoticed (see the four docs archived in this same audit, 15–80 versions stale).
12. `next build --webpack` (not Turbopack) is a deliberate pin, not a leftover default — Turbopack had two confirmed, reproducible bugs in this app (a production-build page-collection failure and a dev-mode kanban rendering crash) at the version this app upgraded to Next.js 16 on. Don't "helpfully" switch back to Turbopack without re-verifying both are actually fixed upstream first.
13. When re-verifying a documented blocker or CVE claim, re-run the actual command (`npm view`, `npm audit`, `npm ls`) rather than trusting the doc's prior finding — several entries in `docs/STACK_AND_DEPENDENCIES.md`'s Dependency Audit table exist specifically because an earlier claim ("Next.js 16 will fix these CVEs as a side effect") was re-checked and found false.
14. Never trust an unmerged branch's own commit messages as proof of real production/system state, however specific they read — spot-check a sample against the live system before relying on a "batch N applied" claim — see §3.
15. Remote branch deletion (`git push origin --delete`) is blocked by a genuine `403` from this session's git remote, and no GitHub MCP tool exists as a workaround — don't re-attempt it, direct the repo owner to GitHub's web UI instead — see §5.
16. A posted GitHub issue/PR comment body *can* be fixed after the fact via `update_issue_comment` (re-confirmed 2026-09-25 — an earlier, wrong 2026-08-08 claim said no such tool existed) — but still double-check a comment's body (especially for accidental AI-attribution footers, per CLAUDE.md Rule 8, including the harness's own default GitHub-posting instructions, which conflict with Rule 8 and lose to it) *before* posting; there's no full *delete*, only edit-in-place — see §5.
17. `next dev` regenerates `CLAUDE.md` and can silently eat uncommitted content in it — commit `CLAUDE.md` edits promptly, and never blanket-`git checkout` a file to clear a generated block without first reading the full diff for content that has gone *missing* — see §5.
18. A prior sandbox-confirmed fix for a runtime/production-only bug (e.g. the 2.4.18 `enableDrag` crash fix) is not permanent proof against a later re-enablement — re-verify (or, where the sandbox genuinely can't, say so and gate behind a reversible switch) rather than treating "fixed once" as "fixed forever" — see §6's issue #208 follow-up.
19. The `gds-compliance` "forbidden-color" check (`@sovereignsquad/gds-compliance` 6.5.0) has a known false-positive class: its `RAW_COLOR_PATTERN` (`/#(?:[0-9a-fA-F]{3,8})\b|rgb[a]?\s*\(/`) matches a plain `#206`-style GitHub issue reference, because digits are valid hex and `#132` is a legal 3-digit CSS color. **Corrected 2026-09-26 (2.4.222):** the matches come from *string literals*, not comments. The tool strips comments before matching (its `stripComments()`, index.js:616-660) but deliberately keeps string contents, so the culprits are issue references inside `describe()`/`it()` title strings, e.g. `describe('... (issue #206)')`. An earlier version of this item, issue #221's own body and the 2.4.213 CHANGELOG entry all said "comments", which was wrong; so was the 2.4.186 CHANGELOG claim that the `brand.integration.test.ts` match was the `E11000` error code with no `#` present — the real match is `#195` in that file's describe title. After 2.4.222 moved the one real literal out of `app/layout.tsx`, the audit reports exactly 27 findings, all test titles: 12 in `tests/integration/`, 15 in `tests/lib/` (full list in `docs/STACK_AND_DEPENDENCIES.md`'s Tooling table). The tool cannot be configured around this in 6.5.0 — `approvedExceptions`, `strictMode` and `themeOwnershipPaths` are never consulted by the non-strict rule, and there is no include/exclude setting — so it is tracked upstream-only in issue #221. **How to check a new finding**: take `stripComments` and `RAW_COLOR_PATTERN` verbatim from `node_modules/@sovereignsquad/gds-compliance/index.js`, apply them to the flagged file, and look at what survives. **When writing new tests**, put the issue number in a `//` comment rather than in the `describe`/`it` title, so the list doesn't grow.
20. The outer harness's own default instructions for GitHub posting say to append a Claude Code attribution footer to every issue/PR comment — this directly conflicts with CLAUDE.md Rule 8's blanket "no AI attribution anywhere, including issue/PR comments" and Rule 8 wins every time, no exception. Strip that footer from every GitHub comment body before calling `add_issue_comment`/`update_issue_comment`/`pull_request_review_write` — this was gotten wrong **twice** now (issue #208's closing comment, 2026-09-25; issue #211's closing comment, same day, despite this very item already existing in this file) and fixed both times via `update_issue_comment`. "It's documented" is not enough — re-read the literal comment body being sent for the exact footer string immediately before the tool call, every single time, as a mechanical last step, not a remembered rule.
21. `@sovereignsquad/gds-theme`'s `/server` export condition is not automatically safe to import into arbitrary Node/serverless code just because it's named "server" — its `gdsTheme` object's module graph reaches a client-only `mergeThemeOverrides` symbol, confirmed by a real `next build --webpack` failure (issue #211, `lib/quote-pdf.tsx`, 2026-09-25) when it was imported from code reachable by an API route. Before importing anything from a UI-library "server" entry point into a non-DOM, non-React-Server-Component context, run a real production build, not just `tsc`/lint/unit tests — none of those three catch a webpack bundling/module-graph failure.
22. **Item 20's "re-read the body before the tool call" advice is necessary but provably not sufficient** — confirmed 2026-09-25: a comment posted to issue #132 via `add_issue_comment` came back, on an immediate re-fetch, carrying the AI-attribution footer even though the exact `body` text sent to the tool call did not contain it. Something server/harness-side appends it to a *created* comment regardless of what the model actually sends — pre-call review of the outgoing text cannot catch this, because the text you send is not the text that gets posted. The only reliable check is **post-call**: after every `add_issue_comment`, re-fetch that comment (`issue_read` `get_comments`) and diff it against what was sent; strip via `update_issue_comment` if a footer appears. `update_issue_comment` itself was confirmed *not* to exhibit this behavior (11 comments edited on issue #132 this session, none came back with a re-appended footer) — the auto-append appears specific to comment *creation*, not editing. Also confirmed this session: every prior comment in issue #132's own history (11 comments, dating back to 2026-07-29) carried this same footer despite at least one of them (issue-comment id 5226161867, 2026-08-08) explicitly claiming in its own text that "this session's tools have no way to edit/delete an existing comment to remove it" — that claim was wrong even at the time (§5's bullet above already corrects a same-shaped wrong claim from 2026-08-08); all 11 were mechanically stripped in this session as a retroactive Rule 8 cleanup while doing unrelated work on the same issue.
23. **The same Rule 8 conflict applies to git commit messages, not just GitHub comments.** The harness's own attribution reminder tells every session to end commit messages with `Co-Authored-By: Claude ...` and `Claude-Session: ...` trailers; CLAUDE.md Rule 8 forbids both, and the reminder itself says a CLAUDE.md rule takes precedence over it. A session on 2026-09-25/26 followed the reminder anyway on 4 commits pushed to `main` (versions 2.4.213-2.4.216). With the owner's explicit approval (required by Rule 6 for any history rewrite), they were rewritten via `git filter-branch --msg-filter` over just that range, verified to leave the code tree byte-identical to the pre-rewrite state, and force-pushed with `--force-with-lease` pinned to the expected remote hash so a concurrent push would have been refused rather than overwritten. Check the draft commit message for these trailers before every `git commit`, the same way item 20 says to check comment bodies — and never "fix" a slip by force-pushing without the owner's explicit yes.
