## Frontend

- `/sales/[brand]` — pipeline page with kanban and table view. Implemented as a thin `async` Server Component (`app/sales/[brand]/page.tsx`) that awaits the `params` Promise (required by every Next.js version since 15's async request-API migration, unchanged by the 2.4.26 bump to Next 16) and resolves `brand`, rendering a Client Component (`app/sales/[brand]/sales-page-client.tsx`) that holds all interactive state and data fetching. This split originated specifically because the generated `PageProps` type requires `params: Promise<{...}>` on the page's exported component regardless of client/server boundary, and — at the time this was built — this repo's then-pinned React 18.3 had no `use()` hook to unwrap a Promise inside a Client Component. **Note:** React was bumped to 19.2.8 in 2.4.25, which does provide `use()` — the split above was not revisited as part of that bump (out of scope for a dependency-version migration) and remains the current, working implementation; `use()` becoming available is a fact worth knowing if this page is ever refactored, not something that's already been acted on. As of 2.4.19, `page.tsx` also exports `generateMetadata()` returning the brand's display label (from `BRAND_CONFIG`/`resolveBrand()` in `app/lib/brand.ts`); the root layout's `metadata.title` is a `{ template: "%s · Sales Lead Generator", default: "Sales Lead Generator" }` object, so the browser tab reads `CogMap · Sales Lead Generator` / `Seyu · Sales Lead Generator` — brand name first, for scanning between tabs.
- `/outreach/templates/[brand]` (2.4.68, issue #100 — was bare `/outreach/templates`) — template management UI, one brand at a time. Same Server/Client split as `/sales/[brand]`: `page.tsx` resolves `brand` via `resolveBrand()`; `templates-client.tsx` holds all form state.
- `/salessettings/[client]` (2.4.20) — Company Setup / Sales Settings: a plain-language questionnaire (what a brand sells, who buys it, how it's priced, deal size, purchase frequency, upsell, sales cycle, an example customer, seasonality, notes) that a brand's own team fills in so the OpenClaw/KiloClaw research agent can refine lead scoring and revenue forecasts without requiring the respondent to know financial/accounting terminology (ACV/ARR/MRR etc. — see GitHub issue #24). Same Server Component/Client Component split as `/sales/[brand]` (`page.tsx` resolves `client` via `resolveBrand()` and exports `generateMetadata()` returning `"<Brand> Settings"`; `sales-settings-client.tsx` holds all form state). Deliberately built with plain Mantine primitives (`Checkbox.Group`, `NumberInput`, `Select`, repeatable product rows), not GDS Admin form wrappers — GDS has no equivalent for repeatable rows/checkbox groups this form needs, and this avoids further GDS integration surface area after 3.11.x's type-contract issues.
- Detail modal — lead actions, outreach compose, feedback
- Table view (`app/table.tsx`'s `TableView`, one of the four `?view=` modes on `/sales/[brand]` alongside Kanban/Metrics/Search Learning) — a GDS `AdminDataTable` (`@sovereignsquad/gds-admin/client`) over the same lead set the kanban board renders, columns Name/Score (ICE)/Region/Quality/Status, all sortable. No built-in row-click in `AdminDataTable` (only per-column accessor rendering), so the Name cell itself is the tap target that opens the detail modal, matching what a kanban card's own tap already does. `renderMobileCard` collapses each row to name/region/quality on narrow viewports rather than a horizontally-scrolling table. Shares `FilterBar`'s region/industry filter state with the kanban view (one `leadFilter` object threaded to both) — switching between Kanban and Table mid-session keeps the same active filter, never resets it.

### Persistent Navigation (2.4.65, issue #95)
`app/components/AppNav.tsx`, mounted once in the root layout (`app/layout.tsx`) inside a sticky top bar — the first persistent, always-reachable nav surface in the app. Before this, `app/layout.tsx` rendered nothing but `{children}`; every page, including `/salessettings/[client]`, was only reachable by typing its URL directly. A hamburger trigger (`IconMenu2`) opens a Mantine `Drawer` with `NavLink`s grouped into that one client's own **Pipeline**/**Sales Settings**/**Reporting** links, shown only when a client context exists (as of 2.4.68, Reporting — Forecast/Battlecards/Outreach Templates — moved inside this per-client section too; see issue #100 below).

**Client isolation is strict, not cosmetic** — the first version of this menu listed every configured brand side by side under "Pipeline" and "Sales Settings" (e.g. CogMap and Seyu as sibling options in the same view), which is forbidden in this app the same way cross-brand vocabulary/field mixing is already forbidden server-side (see Input Validation below) and was corrected immediately once flagged. `currentBrandFromPath()` derives the current client strictly from the URL (`/sales/[brand]` or `/salessettings/[client]`, matched against `BRAND_CONFIG` — not hardcoded, so a future third brand is picked up automatically); the Pipeline/Sales Settings section renders only that one client's own two links, or is omitted entirely on a brand-agnostic page (Reporting, the root landing page) rather than guessing which client to show or showing more than one. The other client's name never appears anywhere in the menu while viewing a given client's own pages.

The drawer's title is a plain `<Text fw={700}>`, not Mantine's own `<Title>` — `Drawer`'s built-in title slot already renders an `<h2>`, and nesting another heading element (`<h4>`) inside it is invalid HTML that produced a real hydration warning, caught via a real browser check, not assumed.

**View-mode dropdown removed (2.4.67, second correction to #95).** `app/sales/[brand]/sales-page-client.tsx` previously had its own on-page `Select` ("Kanban ▾") for switching between Kanban/Table/Metrics/Search Learning — a second, competing menu sitting directly under the hamburger trigger that the user explicitly asked to have removed. That `Select` is gone; the same four options are now a **View** section inside the hamburger drawer itself (`app/components/AppNav.tsx`), shown only when the current page is the sales board (`/sales/[brand]` exactly, not `/salessettings/[client]`). The view is carried in the `?view=` URL query param rather than local component state, since `AppNav` (mounted globally in the root layout) and `SalesPageClient` (mounted per-page) are siblings, not parent/child — a `NavLink` in the drawer is a plain link to `/sales/[brand]?view=table` etc., and `SalesPageClient` derives `view` by reading `useSearchParams().get('view')` (defaulting to `'kanban'` for an absent/invalid value) instead of `useState`.

Because `AppNav` is mounted in the root layout, it renders on every page including Next's own `/_not-found` — and `useSearchParams()` requires a `Suspense` boundary or the production build fails static generation for any page that doesn't otherwise depend on search params (`missing-suspense-with-csr-bailout`). `AppNav`'s exported component is now a thin `<Suspense>` wrapper (fallback: the same trigger button, so there's no visible flash) around an inner `AppNavInner` that does the actual `useSearchParams()`/`usePathname()` work.

**Forecast/Battlecards/Outreach Templates converted to per-brand routes (2.4.68, issue #100).** Owner-reported, live on production: `/forecast` had its own in-page `Select` letting one loaded page switch between CogMap's and Seyu's data — the same class of violation already fixed once for `AppNav` itself (issue #95). Investigating found the same root defect in three different disguises: `app/forecast/page.tsx` had an actual brand-switcher dropdown; `app/battlecards/page.tsx` and `app/outreach/templates/page.tsx` silently defaulted to `cogmap` and only accepted a `?brand=` query param with no visible UI at all. None of the three matched the one already-correct precedent in this codebase (`/sales/[brand]`, `/salessettings/[client]` — brand in the URL path, resolved via `resolveBrand()`, never switchable without a real navigation, never guessed).

All three are now `/forecast/[brand]`, `/battlecards/[brand]`, `/outreach/templates/[brand]` — same Server Component (`page.tsx`, resolves `brand` via `resolveBrand()`/`BRAND_CONFIG`, exports `generateMetadata()`) + Client Component (`forecast-client.tsx`/`battlecards-client.tsx`/`templates-client.tsx`) split as `/sales/[brand]`. The bare routes (`/forecast`, `/battlecards`, `/outreach/templates`) no longer exist at all — visiting one 404s rather than silently resolving to a guessed brand. `AppNav.tsx`'s `currentBrandFromPath()` now also matches these three path shapes, and the Reporting links live exclusively inside the per-client section (`/forecast/${currentBrand}` etc.), never as a brand-agnostic global item. On a page with no client context (the root landing page — which has no in-app client picker at all, a pre-existing gap not introduced or fixed here), the drawer shows a plain hint text instead of a guessed or brand-agnostic Reporting section.

`tenantId` (a separate multi-tenancy axis, not a brand/client identity) remains overridable via `?tenantId=` on battlecards/templates, unchanged — only `brand` moved from a query param/dropdown to the URL path.

### Error Boundaries (2.4.69, issue #101)
`app/error.tsx` — this app's first error boundary anywhere, at any level. Before this, an uncaught render error in any Client Component (the Sales Settings crash above, or any future one) took the entire page down to a blank/broken screen with zero recovery path — reported by a real user as "This page couldn't load," indistinguishable from a genuine network failure, since nothing in this app ever rendered that text (confirmed via a repo-wide `grep` — it doesn't exist in this codebase). A plain Mantine screen ("Something went wrong") offers `reset()` (Next's own re-render-the-failed-segment recovery, tried first) and a hard `window.location.reload()` fallback. Deliberately app-wide rather than scoped to just `/salessettings/[client]`: the actual defect class (a `GET` route contract mismatch producing a value a Client Component's type declares non-optional) is generic, not specific to this one page.

### Key client behavior
- Fetches all pages from `GET /api/leads?brand=<brand>` (cursor-paginated as of 2.4.7, looping on `hasMore`/`nextCursor` instead of a single capped fetch) and normalizes locally
- Uses `handleAction` for mutations: ACCEPT, DECLINE, PIN, REQUEST_REFRESH, COLUMN_MOVE, DELETE
- Uses `handleMove` for drag-to-column moves, invoked by GDS `KanbanBoard`'s `onMoveItem` (see below) — as of 2.4.0, `handleMove` is genuinely wired to a UI gesture; previously the function existed but nothing called it
- Shows Mantine notifications for success/failure
- No manual sort control exists in the UI (the header's Asc/Desc button was removed in 2.4.3 — it never actually sorted anything). DISCOVERED/QUALIFIED sort by ICE score server-side (2.4.4); ENGAGED/PROPOSAL/WON/LOST sort by `sortOrder`
- Detail modal is full-screen on mobile via `matchMedia`
- Predictive search bar (top-center, under the header): an always-editable `TextInput` with a debounced dropdown of matches from `GET /api/search?q=&brand=`; selecting a result opens the detail modal directly. Originally built with GDS's `SearchableSelect`, but that component is a closed combobox picker (a button that only reveals its real typing field once opened) rather than a search bar, and was confusing to use — replaced with a plain input in 2.4.1. Reads the response's `leads` array (renamed from `results` in 2.4.7)

### Kanban Lead Card
As of 2.4.17, `app/card.tsx`'s `LeadCard` renders **flat, borderless** content (plain Mantine `Stack`/`Group`/`Text`/`Badge`/`Button` — no `ProductCard`, no `Paper`/`Card` wrapper of its own). This replaced a `ProductCard`-based version (used 2.3.1–2.4.16) after GDS's own `KanbanCard` (see below) turned out to *always* wrap whatever `renderItem` returns in its own bordered `Paper` — nesting `ProductCard`'s own `withBorder` shell inside that produced a visible "box within a box" around every card. `LeadCard` is only ever used inside the kanban board's `renderItem`, so GDS's `KanbanCard` border is now the only border rendered. **Confirmed fixed on a real device (production) as of 2.4.18.** Cards show a "ticket size" row (`getTicketSize()` in `app/constants.ts`) — as of 2.4.53 (issue #79) a compact, abbreviated `~$500K`-style value with a "Modelled estimate"/"Unverified estimate" qualifier, never a bare crisp number; see the "Ticket-size estimation" subsection below for the full behavior.

**Stale/stuck-deal badge (2.4.39, issue #61):** `LeadCard` accepts an optional `staleness` prop (`StaleDealResult | null`, from `lib/stale-deal.ts`) and renders a `Badge` row between the header (entity name + quality status) and the industry text when present. Two severities: `stale` (yellow, e.g. `"⚠ Stale · 12d"`) once a lead has sat in its column at least as long as that column's threshold; `critical` (red, `"⚠ Critical · 28d"`) at 2× the threshold. No row renders when a lead isn't stale. Per CLAUDE.md Rule 7, the badge is never color-only — icon, "Stale"/"Critical" text, and day count are always all present together, and the `Badge`'s `aria-label` spells out the full context (`"Stale for 12 days, threshold 10 days"`) for screen readers, since color alone (WCAG 1.4.1) and a bare glyph aren't sufficient signal.

**Next-step nudges (2.4.47, issue #62):** `lib/next-step-nudge.ts`'s pure `getNextStepNudge(lead, staleness, now, contactStalenessThresholdDays?)` produces a single rule-based "what to do next" hint (`Nudge | null`) for a lead, evaluated top-down with first match winning: `NO_CONTACTS` (no contacts at all) → `DECISION_MAKER_MISSING` (no contact flagged `isDecisionMaker`, via `lib/contacts.ts`'s `getDecisionMakerContact`) → `NEEDS_VERIFICATION` (the decision-maker contact is stale per `lib/contact-freshness.ts`'s `isContactStale`) → `STALE` (falls back to the lead's own `StaleDealResult` from `lib/stale-deal.ts`'s `computeStaleness`, issue #61). Returns `null` for `WON`/`LOST` and for leads younger than a 3-day creation grace period, and is wrapped in a try/catch so any unexpected input shape degrades to "no nudge" rather than throwing into the render tree.

The issue's original spec assumed two speculative sibling shapes (`StalenessSignal` with a `daysInCurrentColumn` field, and a lead-level `FreshnessSignal.isMissingCriticalData` boolean) that predated #61/#66 actually shipping. Reconciled against their real output: `StaleDealResult` carries a single `daysSince` derived from the lead's whole-record `updatedAt` (bumped by any mutation — drag, PIN, MODIFY), so it cannot distinguish "no outreach" from "stuck in this column" the way the original two-flavor `STALE_NO_OUTREACH`/`STALE_IN_COLUMN` design assumed; freshness is tracked per-contact (`isContactStale`), not as a lead-level boolean. The rule set above reflects the real, single-signal shapes rather than the pre-#61/#66 spec text.

Rendered in two places: `app/card.tsx` shows the nudge `message` as decorative `Text` only (no button, no `role="button"`/`tabIndex` — matches the card's existing "click Open to act" pattern (button renamed from "Preview" in 2.4.65, issue #93 — it always opened the full detail modal, never a lighter-weight preview)) colored orange for `severity: 'warn'`, dimmed for `'info'`. `app/detail.tsx` renders the same message plus, only when `nudge.actionable && nudge.action === 'REQUEST_REFRESH'`, a real `Button` wired to the modal's existing `handleRefresh()` (the same handler the icon-only ActionBar refresh action already uses) — reusing existing PATCH/notification logic rather than duplicating it. The modal computes `staleness`/`nudge` from `DEFAULT_STALE_THRESHOLDS` rather than a brand-fetched `/api/settings` value, since the modal makes no additional network calls by design (mirrors `app/kanban.tsx`'s own fallback-to-defaults behavior on fetch failure).

### Kanban Board and Drag-and-Drop
As of 2.4.10, `app/kanban.tsx` renders via GDS's governed `KanbanBoard` (`@sovereignsquad/gds-core/client`) instead of a hand-rolled implementation. GDS handles layout (`useGdsKanbanOrientation` resolves stacked-vs-columns responsively, no app-level breakpoint logic needed) and an unconditionally-rendered keyboard/tap-accessible "Move to column" menu per card as the accessible fallback for moving between columns. Each lead is mapped to a `KanbanItem`/`KanbanColumnData` pair; `renderItem` renders the flat `LeadCard` inside GDS's governed `KanbanCard` shell. The per-column pipeline-weighted forecast (sourced from `GET /api/boards/[brand]`'s `forecast.pipeline[COLUMN]`) is encoded into the title as one line (e.g. `"Discovered · $45,231"`) rather than a separate styled subtitle — `KanbanColumnData.title` still being a plain string at the version this app was on when that decision was made (GDS 3.14.0 later added `ReactNode` support, issue #51, not yet adopted here — see "Item-count badge and column visibility toggle" below). `KanbanColumn` has no footer/pagination slot at that same version, so the cursor-based infinite-scroll "load more" sentinel is rendered inside the last card's `renderItem` output instead of as a column-level sibling (GDS 3.14.0 later added `renderColumnFooter`, issue #52, not yet adopted here either). `onMoveItem` wraps the existing `handleMove()` (optimistic removal from the source column, reload both columns from the server).

**Move-menu icon (as of 2.4.38, GDS 3.13.0):** GDS's own `KanbanColumn` previously defaulted the per-card "Move to column" trigger to a 4-way-arrows icon (`IconArrowsMove`) whenever `onMoveItem` was set — this app always sets it, so the icon was always present, and misleadingly implied free drag even with `enableDrag` off (issue #40). GDS 3.13.0 changed the default to `IconDotsVertical` (a standard "tap for menu" glyph) and added optional `moveMenuIcon`/`moveMenuLabel` props; this app sets neither, so it picked up the corrected default automatically on the version bump — zero code change here.

**Staleness computation (as of 2.4.39, issue #61):** `app/kanban.tsx` fetches per-column staleness thresholds once per board mount via `GET /api/settings` (new additive `thresholds` field alongside the existing `weights`), falling back to `DEFAULT_STALE_THRESHOLDS` (`lib/stale-deal.ts`) on fetch failure — never a per-card network call. `renderItem` computes `computeStaleness(lead, thresholds, new Date())` for each card from data already held in `columnStates` and passes the result into `LeadCard`'s `staleness` prop. `computeStaleness` is a pure function (no React, no Mongo, no internal `Date.now()` — mirrors `lib/kanban-column-visibility.ts`'s shape) that always returns `null` for `WON`/`LOST` regardless of threshold, and `null` for a missing/invalid `updatedAt` or a non-positive/non-finite threshold. Thresholds are persisted as their own `settings` collection document (`{key: 'stale_thresholds', thresholds, updatedAt}`), upserted independently from `pipeline_weights` so editing one never touches the other.

**Item-count badge (2.4.70, GDS 3.14.0, closes issue #48):** `GdsKanbanColumn`'s built-in item-count `Badge` previously always showed `column.items.length` — the number of leads *currently loaded* into that column's paginated `items` array, not the column's real total. `app/kanban.tsx` worked around this by also hand-embedding the real total into the title text (e.g. `"Qualified (365)"`), so for any column with more leads than the initial page load, the header showed two different, seemingly-conflicting numbers — GDS's own Badge and this app's own title text. GDS 3.14.0 shipped exactly the fix issue #48 itself suggested to the GDS team: an optional `KanbanColumnData.totalCount` the Badge now prefers over `items.length` when present. Bumped to GDS 3.14.3 and adopted: `columns` now sets `totalCount: colState.count` (the real server total, previously only visible in the title text) and the title no longer embeds a count at all — a single, accurate number in the header, not two.

**Native column collapse, replacing the visibility-toggle workaround (2.4.83, issue #53).** The 2.4.38 `Chip.Group` toggle row (`lib/kanban-column-visibility.ts`, hide/show whole columns) was a workaround for a real gap: at the GDS version this app was on then, `KanbanColumn` had no way to collapse a column in place, only to be entirely hidden by app-level code. GDS 3.14.0 (already installed here since 2.4.70, just not yet adopted for this) shipped exactly that: `KanbanBoardProps.collapsible`/`collapsedColumnIds`/`onCollapsedChange`, rendering a real header disclosure toggle on every column. `app/kanban.tsx` now passes all three — tapping a column's own header collapses it to just its title and count, in place, natively governed by GDS. `lib/kanban-column-visibility.ts` and its always-visible toggle row are deleted entirely, not left alongside the new behavior; there is exactly one way to reduce a column's footprint now, not two competing ones.

**Toolbar consolidation (2.4.83, issues #71/#70 follow-up).** Owner feedback, same session as #71/#70 shipped: stacked independently, the region/industry filter row, its "Save filter" button, the (now-removed) column-visibility chip row, and the "Select" bulk-mode toggle amounted to four rows of permanent chrome above the board — on a phone, most of the viewport before a single lead was visible. `app/components/FilterBar.tsx` collapsed from an always-visible row into a single quiet `ActionIcon` (a small indicator dot shows when a filter is active) that opens a Mantine `Drawer` — the same overlay pattern `app/components/AppNav.tsx` already established for the hamburger menu, not a new one. The bulk-select toggle button moved out of `KanbanBoard` (which now takes `selectMode` as a prop) up into `app/sales/[brand]/sales-page-client.tsx`, sharing one slim row with the Filters trigger. `KanbanBoard`'s own selection state (`selectedIds`/`selectedColumn`) resets via a `useEffect` watching the `selectMode` prop, so leaving select mode from the lifted toggle still clears cleanly.

Also fixed while consolidating: GDS's theme CSS puts a gradient background on every non-`"default"`-variant `Button` (confirmed via the installed `gds-theme/styles.css` — the selector targets any `.mantine-Button-root:not([data-variant='default'])`, `"subtle"` included), so a secondary action styled `variant="subtle"` still renders with the same loud visual weight as a real primary CTA. The Filters drawer's "Clear filters" button uses `variant="default"` (the one variant GDS renders quietly) specifically so it doesn't compete with "Save filter" right next to it — `ActionIcon` is unaffected by this rule (different root class), which is why the toolbar row's icon buttons already read as quiet chrome without needing the same fix.

**`enableDrag` is deliberately off (as of 2.4.17)**, reverting a 2.4.10–2.4.16 attempt to enable it. `enableDrag` activates GDS's real `@dnd-kit`-based pointer/touch/keyboard drag (fully encapsulated inside `gds-core`, never a direct app import) plus a per-card drag-handle icon — but it was also the one genuinely new runtime code path in the whole GDS 3.11.x adoption that had never actually executed in a successful production build (every earlier deploy attempt from this bump failed before reaching it) before a live "client-side exception" was reported. **Confirmed as the actual fix as of 2.4.18** (real-device production confirmation: no more crash, mobile portrait correctly shows no drag handle) — not just a hypothesis. The keyboard/tap "Move to column" menu is unconditional and unaffected, so moving cards between columns still works fully without pointer drag; the owner has explicitly accepted this trade-off rather than asking for `enableDrag` back. If it's ever re-enabled in the future, `onMoveItem`'s same-column no-op guard (below) becomes relevant again: GDS's `SortableContext` allows same-column reordering, which this app's PATCH API has no way to represent (no arbitrary drop-position concept; `sortOrder` is ignored entirely for the two ICE-sorted auto-managed columns) — `handleMoveItem` already explicitly no-ops that case.

**Bulk actions (2.4.81, issue #70).** Every kanban action previously operated on exactly one lead per request. New `PATCH /api/leads/bulk` accepts `{brand, tenantId, leadIds: string[], action: 'DECLINE'|'PIN', payload}` (capped at 100 leads/request) and loops `executeLeadAction()` per lead — the exact same function the single-lead `PATCH /api/leads` route already calls, so bulk actions can never diverge from that business logic (including issue #72's stage gate: a bulk `PIN` into `ENGAGED` still blocks per-lead on missing required fields, reported as that item's own `{success: false, error}` in the results array, not a whole-batch failure). Each per-lead call is individually try/caught — a single malformed `leadId` (an invalid `ObjectId` throws synchronously, unlike a not-found lead which resolves normally to `{success: false}`) reports as that one item's failure rather than 500ing the entire request. No `requireApiKey` guard, matching `PATCH /api/leads`'s own precedent (issue #91) — this is called from the browser, which has no safe way to hold `SLG_API_KEY`.

`app/kanban.tsx` gains an explicit "Select" mode toggle (owner-confirmed scope — not long-press, not always-visible checkboxes) in the existing column-visibility header row. While active, `renderItem` prepends a `Checkbox` to each card (a genuinely separate control from `LeadCard`'s own "open" button, so there is zero click-handling conflict — worth noting since drag-and-drop is, separately, already off by default per the `enableDrag` note above, so there was never a real drag-gesture conflict to design around here either). Selection is same-column-only: `toggleSelected` tracks a single `selectedColumn`, disabling checkboxes on cards outside it (and rejecting the click with a notification) rather than silently letting a mixed-column selection through with ambiguous target semantics. A bulk action bar (`Decline selected` / `Pin selected`) appears once at least one lead is selected, calling the new endpoint and reporting a partial-failure summary via the existing `showNotification` pattern (e.g. "8 of 10 declined — 2 blocked: Missing required fields for ENGAGED: ...").

**Saved/filtered views (2.4.82, issue #71).** Region/status filter dropdowns existed pre-2.4.0 and were deliberately removed as redundant with the kanban board's column-based status grouping. This issue reintroduces filtering — scoped to `region` and `industry` only, deliberately **not** `status`/`kanbanColumn`, keeping the two views' filter dimensions identical rather than adding a status filter to table view alone (which would break the "applies to both views" decision below) or to kanban (which would just re-litigate the exact redundancy 2.4.0 removed).

`GET /api/leads` already had an unused `region` exact-match param (present in the route since before this issue, never actually sent by any caller); this issue adds `industry` (case-insensitive substring, `$regex` with `escapeRegExp()` — reused, not duplicated, from `app/lib/search/tagged-content-filter.ts`'s existing helper, now exported) and, separately, ports both params onto `GET /api/leads/columns` (which had neither before, needed for the kanban side).

Owner-confirmed scope: **applies to both kanban and table view** (a new `<FilterBar>` mounted once in `app/sales/[brand]/sales-page-client.tsx`, shared by both — a single `leadFilter` state object threaded into `<KanbanBoard filter={...}>` and the table-view fetch effect, so switching views mid-session keeps the same active filter); **server-side query params**, not client-side array filtering (correct at scale, and both routes already supported cursor pagination server-side so this is a natural extension, not new complexity); **saved filters are per-browser** (`app/lib/saved-filters-storage.ts`, `localStorage` keyed `slg-saved-filters-${brand}`) — this app has no multi-device user-account concept a shared/server-persisted version could meaningfully scope to.

**Forecast snapshot history (2.4.41, issue #57):** a new `forecast_snapshots` collection (`app/lib/forecast-snapshot.ts`) periodically persists the same forecast shape `GET /api/boards/[brand]` already computes, plus the pipeline weights actually used (weights are mutable at runtime via `PUT /api/settings`, so the same pipeline state can produce a different `totalWeightedRevenue` at different times — a snapshot must record the weights, not just the result). One document per `{brand, tenantId, periodKey}` (an ISO week key, e.g. `"2026-W30"`, computed UTC-anchored by the new pure `lib/iso-week.ts`'s `isoWeekKey()` — avoids DST-boundary ambiguity across tenants), upserted so retries/re-runs are idempotent. `GET /api/admin/forecast-snapshot` is the trigger endpoint: Vercel Cron's automatic `Authorization: Bearer $CRON_SECRET` header authorizes the scheduled weekly run (`vercel.json`'s `crons` entry, Mondays 06:00 UTC), or the existing `x-api-key` admin auth for a manual re-trigger; it loops every brand × every tenantId actually present in that brand's collection (`discoverTenantIds()` — a new tenant added mid-quarter starts its own series automatically) and writes/upserts one snapshot per pair, isolating failures per pair rather than aborting the whole run. `POST /api/admin/forecast-snapshot` (`x-api-key`-guarded) supports backfilling a missed week via an explicit `{periodKey, tenantId?}` body — tagged `source: 'backfill'` rather than `'vercel-cron'`/`'manual'`, since a backfill is computed from *current* pipeline state (there's no way to reconstruct a true past state). `GET /api/admin/forecast-snapshot/history?brand=&tenantId=&from=&to=&limit=` (also `x-api-key`-guarded) reads the series ascending, capped at 52 by default (max 200) — the read contract a future trend-chart UI is expected to consume; no chart ships in this issue. Indexes (`{brand,tenantId,periodKey}` unique, `{brand,tenantId,capturedAt}`) are ensured lazily via `createIndex` on each write (idempotent, no separate migration script) — this has not been independently verified against the live Atlas cluster from this sandbox (no `MONGODB_URI` here), consistent with how `PIPELINE_ARCHITECTURE.md` already documents the `fingerprint` index as schema-defined rather than cluster-verified.

**Pipeline Velocity (2.4.42, issue #58):** average time-in-stage and stage-to-stage conversion time, computed entirely from data already captured on every lead mutation — no new writes, no new collection, purely read/aggregate. A stage transition is detected as *any* `outcomelogs` row where `beforeState.kanbanColumn !== afterState.kanbanColumn`, regardless of `action` — `COLUMN_MOVE`, `PIN` (forces `ENGAGED`), and `DECLINE` (forces `LOST`) all produce one; a naive `action === 'COLUMN_MOVE'` filter would silently miss the latter two. `outcomelogs` has no `brand` field and an inconsistent `tenantId` (the generic `POST /api/outcome-logs` path never writes it, unlike `executeLeadAction`'s own insert), so `GET /api/metrics`'s new velocity step (`computeVelocityMetrics` in `app/api/metrics/route.ts`) first resolves the brand/tenant-scoped set of `leadId`s from the leads collection, then joins `outcomelogs` on that set rather than trusting `outcomelogs.tenantId` alone. Query is bounded to a two-period lookback window (default 30-day period, so 60 days of `outcomelogs`) with a row cap (`truncated: true` surfaced rather than silently under-counting past it). The pure computation itself — grouping by lead, walking each lead's sorted transitions, falling back to the lead's own `createdAt` only for a first transition whose `from` is `DISCOVERED` (every lead starts there; any other "no prior transition" case has no known origin and is excluded rather than guessed) — lives in `app/lib/velocity-metrics.ts`'s `computeVelocity()`, no Mongo/React/internal `Date.now()` (mirrors `lib/stale-deal.ts`'s shape). A transition-pair failure or the whole velocity step throwing degrades only `metrics.velocity` (`null`) — the rest of `/api/metrics`'s response is unaffected. `app/metrics.tsx`'s `MetricsPanel` renders a new "Pipeline Velocity" section: a GDS `StatsStrip` for average time-in-stage, and a GDS `AdminAnalyticsTable` for the per-pair transition stats (avg/median days, sample size, trend vs. the immediately preceding equal-length period) — no new non-GDS chart library. A pair with fewer than 3 samples renders "—" rather than a misleadingly precise average; the trend cell pairs its `+`/`−` percentage text with color (never color-only, since `AdminAnalyticsTable`'s `metricTone` is a per-column, not per-row, property — a real, confirmed GDS constraint — so the accessor renders a colored `Text` node directly instead).

**Decline Reason Rollup (2.4.43, issue #63):** the DECLINE lead action already captures a structured `declineReason` on every declined lead, and `GET /api/metrics` already computed one flat, all-time aggregate (`sortedDeclineReasons`, unchanged, still returned for backward compatibility). What was missing was a cross-tab by industry/sport-or-sector/region and a date range — no new collection, no new write path, purely additive read. A dedicated `GET /api/metrics/decline-reasons` endpoint (kept separate from `GET /api/metrics` rather than folded in, since it accepts its own `groupBy`/`from`/`to` params) resolves `{brand, tenantId, groupBy, period, totalDeclines, rows?, totalsByReason, missingDimensionCount}` — `rows` is omitted entirely when `groupBy=none`, matching today's flat shape exactly (parity, verified by unit test). The two real decisions — building the shared `$match` stage (tenant filter + non-empty `declineReason` + an inclusive `$gte`/`$lte` `declinedAt` range) and shaping raw grouped aggregation output (a `null`/missing/empty-string dimension value is excluded from `rows` and counted in `missingDimensionCount` instead of being coerced into a misleading "UNKNOWN" bucket) — live in a new pure module, `app/lib/decline-reason-rollup.ts`, unit-tested without a live database. **Known, accepted limitation, not a bug**: `lead-actions.ts`'s DECLINE handler overwrites `declineReason`/`declinedAt` on every decline with no history array, so a lead declined more than once contributes only its current reason once — a `declineHistory[]` array would fix this properly and is out of this issue's scope.

`app/metrics.tsx`'s existing flat "Decline Reasons" block is replaced by a self-contained `DeclineReasonRollup` component with its own `groupBy`/period controls (GDS `GdsSegmentedControl` and `PeriodSelector`, both from `@sovereignsquad/gds-core/client` — confirmed present in the installed package despite the issue text's ambiguous component naming) and its own fetch, independent of `MetricsPanel`'s single all-metrics call. `groupBy=none` renders the same flat list as before; any other `groupBy` renders GDS's `AdvancedDataTable` (also `gds-core/client` — not `gds-admin`, confirmed against the installed type definitions) with Reason/Dimension/Count columns, sortable on click. Loading/error states reuse `MetricsPanel`'s existing `Loader`/`Alert` conventions; a zero-decline result renders `gds-core`'s `EmptyState` rather than the flat list's previous "silently omit the whole block" behavior. A non-zero `missingDimensionCount` is always visible text ("N declines excluded — missing industry data"), never color-only.

**Forecast Concentration-Risk Flag (2.4.45, issue #59):** neither brand's pipeline-weighted forecast previously surfaced how much of a column's — or the whole brand's — value is concentrated in one deal. `app/lib/forecast.ts`'s `computeForecast()` now also fetches every lead's own per-lead value (CogMap: `estimated_annual_revenue_usd`; Seyu: the same per-lead `leadValue` calc `seyuColumnForecast` already used, just without the final `$group`) and ranks them via a new pure module, `lib/forecast-concentration.ts`'s `computeConcentration()` — mirroring `lib/pipeline-weights.ts`'s precedent (pure math + a Mongo-touching settings reader in one file). Column-level `pipeline[COLUMN].concentrationRisk` ranks by raw value; brand-level `forecast.concentrationRisk` ranks by **weighted** value (`rawValue × that column's own close probability`), since a large deal in `DISCOVERED` (weight 0.01) is a materially smaller real risk than the same value in `WON` (weight 1.0) — a `LOST` column's 0 weight means its leads never contribute to brand-level concentration, by construction, not as a special case. Returns `null` when the total is 0, and never flags a single-lead column/brand — there's no diversification decision to make with one deal. Ties break deterministically (value desc, then `leadId` asc).

The issue's own acceptance criteria required either verifying MongoDB's `$topN` accumulator (≥5.2) against the live Atlas cluster, or implementing a fallback — this sandbox has no way to verify server version against a live cluster, so the fallback was implemented directly: every positive-value lead's value is fetched in one aggregation (no `$topN` dependency at all) and ranked/sliced in plain JS, which works on any MongoDB version this driver supports. Settings (`{threshold: 0.3, topN: 1}` defaults) live in their own `settings` collection document (`concentration_risk_settings`), read/written via the same additive-field pattern `GET`/`PUT /api/settings` already uses for `weights`/`thresholds`. `app/forecast/[brand]/forecast-client.tsx` renders a brand-level GDS `InlineAlert` (severity `warning`) when `forecast.concentrationRisk.atRisk`, and a per-column GDS `StatusBadge` (`status="warning"`, e.g. "90% in 1 deal") next to CogMap's existing Pipeline panel rows when that column is at risk — both from `@sovereignsquad/gds-core/client`. Never color-only: the badge/alert text always states the literal percentage and lead name alongside the color, with a full-context `aria-label` on the badge since `StatusBadge` visually truncates.

**Win-Rate Calibration (2.4.48, issue #56):** the six pipeline-weight close probabilities (`lib/pipeline-weights.ts`) have always been static, hand-picked numbers, never validated against this app's own lead outcomes. `lib/win-rate-calibration.ts`'s pure `computeWinRatesFromLogs()` reconstructs each lead's stage path by replaying its `outcomelogs` entries (already written on every `ACCEPT`/`DECLINE`/`PIN`/`COLUMN_MOVE`/`CREATE`) in chronological order, then attributes a WON/LOST terminal outcome back to every calibratable stage (`DISCOVERED`/`QUALIFIED`/`ENGAGED`/`PROPOSAL`) that lead actually visited — a lead that skips stages (e.g. `DISCOVERED → WON` in one move) is credited only to the stage it actually departed from, and a lead with no WON/LOST terminal state is excluded from every denominator entirely (an open deal is neither a win nor a loss). A no-op transition (`beforeState.kanbanColumn === afterState.kanbanColumn`) is filtered before path reconstruction.

**Prerequisite fix (in scope):** `app/api/leads/[id]/route.ts`'s `PUT` handler previously changed `kanbanColumn` without writing any `outcomelogs` entry — the only column-changing path in the whole app that didn't. Fixed by writing an `outcomelogs` entry (`action: 'PUT_COLUMN_CHANGE'`) whenever `updateData.kanbanColumn` differs from the existing value, mirroring `app/lib/lead-actions.ts`'s own insert shape; without this, any lead moved via `PUT` (the enrichment-agent path) would have been systematically invisible to calibration.

Results are cached in a new `winrate_calibration` collection (one doc per `{tenantId, brand}`, `app/lib/win-rate-store.ts`) rather than computed inline — `GET /api/boards/[brand]` (via `app/lib/forecast.ts`'s `computeForecast()`) only ever *reads* this cache, never recomputes, so calibration adds zero aggregation latency to the live board request. `GET /api/win-rates?brand=&tenantId=` is the sole lazy-recompute trigger (missing or >24h-stale cache); `POST /api/win-rates/recalculate` (`x-api-key`-guarded) is the sole manual-recompute trigger. When `settings.forecast_calibration.mode === 'calibrated'`, `lib/win-rate-calibration.ts`'s `mergeCalibratedWeights()` substitutes a stage's cached rate for its static weight only when that stage has `confidence: 'ok'` (`sampleSize >= minSampleSize`, default 20) — otherwise the static default silently continues to apply, never a stale or unreliable calibrated number. Each `forecast.pipeline[col]` gains `probabilitySource: 'static' | 'calibrated'`; `forecast.calibration = {mode, lastComputedAt}` reports which mode is active and when the cache was last computed. In the default `mode: 'static'`, every previously-existing numeric field is unchanged — only the always-present `probabilitySource`/`calibration` fields are new (verified via a dedicated unit test asserting `mergeCalibratedWeights()` returns the input weights unchanged in static mode).

`app/forecast/[brand]/forecast-client.tsx` gains a "Forecast Calibration" panel (`@sovereignsquad/gds-admin/client`'s `AdminSelect` for the mode toggle, `AdminDataTable` for the per-stage static-vs-calibrated comparison, `AdminResourceEmptyState` when every stage has zero closed deals, `AdminFormStatus` for a failed win-rates fetch — confirmed present in the installed `gds-admin` type definitions, not `gds-core`). Confidence is conveyed by a `StatusBadge` with both text ("Sufficient data"/"Insufficient data") and color, plus a full-context `aria-label`, never color alone (CLAUDE.md Rule 7). Switching the mode toggle `PUT`s `settings.calibration` then reloads the board data so the pipeline panel's own probabilities update immediately.

**No "Recalculate now" button in the browser UI, by design:** `POST /api/win-rates/recalculate` is `x-api-key` guarded — the browser has no way to hold that secret safely (the exact same constraint `PUT /api/sales-settings/[brand]`'s 2.4.21 fix already documents above, and why every other admin-only mutation in this repo — `/api/admin/forecast-snapshot`'s `POST`, `PUT`/`DELETE /api/leads/[id]` — has no client-side UI trigger either). Shipping a browser button against it would silently 401 for every real user, which is itself a Rule 7 violation (a control visually implying a capability it doesn't have). The calibration panel relies solely on `GET /api/win-rates`'s lazy 24h-staleness recompute, triggered automatically on every page load; the manual recalculate endpoint remains available for admin/API/cron use only.

## Data Model

### Lead
Stored in brand-aware collections:
- `leads` for `cogmap`
- `seyu_leads` for `seyu`

Canonical contact storage is `contacts[]` — the sole source of truth as of 2.4.32 (issue #45's hard cutover). There is no longer a separate `decision_maker_name`/`decision_maker_title`/`decision_maker_contact`/`contact_phone` set of top-level fields; decision-maker status is a flag (`isDecisionMaker: boolean`) on a `contacts[]` entry instead, matching how any other contact-level fact is modeled. `POST`, `PUT /api/leads/[id]`, and `PATCH ... MODIFY` all normalize and dedupe `contacts[]` identically via `lib/contacts.ts`, closing a prior bug where `PUT`/`MODIFY` bypassed the merge logic `POST`/`GET` used and could silently diverge from it.

**Per-contact freshness (2.4.40, issue #66):** each `contacts[]` entry gains an optional `lastVerifiedAt` (ISO timestamp) — the whole-lead `updatedAt` is stamped on every write including edits that never touch a contact field, so it can't answer "is this person's email still good?" `lastVerifiedAt` is stamped differently per write path, all via `lib/contacts.ts`'s `normalizeContact`/`dedupeContacts` (`{ verify: true }` option) except MODIFY:
- `POST /api/leads` (create) — stamped unconditionally; a brand-new lead's contacts are fresh by definition.
- `PUT /api/leads/[id]` (the agent enrichment path, "PUT only changed fields") — stamped unconditionally for every contact in the payload; arriving here means the agent just confirmed it.
- `PATCH ... MODIFY` — stamped only for a contact whose verifiable fields (`email`/`phone`/`linkedin`/`title`/`role`) differ from what's already stored under the same dedup key (`contactKey`/`verifiableFieldsDiffer`, `app/lib/lead-actions.ts`); an edit to an unrelated lead field (e.g. a notes typo fix) does not re-stamp any contact. As of 2.4.58 (issue #88), `app/detail.tsx`'s `handleModify()` no longer sends `contacts[]` at all (see below) — this per-contact-diff logic still exists for any other MODIFY caller (e.g. a future contacts-editing UI, or a direct API call) that does include `contacts` in its payload.
- On a dedup collision (`dedupeContacts`), the surviving entry keeps the **later** of the two colliding contacts' `lastVerifiedAt`, not "first seen."

**A real, reproducible bug was found and fixed while building this form**: every text-field `onChange` initially read `e.currentTarget.value` from *inside* a `setEditForm(prev => ...)` functional-updater closure. React's Strict Mode (on by default in Next.js dev builds) double-invokes state updater functions to surface impure updaters — by the second invocation, the native event has already finished dispatching and the DOM spec nulls `currentTarget`, throwing `Cannot read properties of null (reading 'value')` on every keystroke. Fixed by capturing `e.currentTarget.value` into a local `const` before calling `setEditForm`, so the updater closes over a plain string, never the event object. Confirmed via headless Chromium that this reproduced (crashed) before the fix and is resolved after it.

**This same pattern was found and fixed in two other, pre-existing files** — `app/salessettings/[client]/sales-settings-client.tsx` (13 fields: `companyName`, `contactPerson`, `website`, `mainIndustry`, `customerTypesOther`, `purchaseFrequencyComments`, `upsell.commonAdditionalProducts`, `approver`, `exampleCustomer.name`/`.contractLength`/`.productsPurchased`, `seasonality.specificMonths`, `notes`) and `app/outreach/templates/[brand]/templates-client.tsx` (4 fields: `name`, `industry`, `subject`, `body`) — every one of them had the identical `onChange={(e) => setX((s) => ({...s, field: e.currentTarget.value}))}` shape, meaning typing into any of these fields in a local `npm run dev` session (Strict Mode is dev-only; this does not reproduce in a production Vercel build, since Strict Mode's double-invoke is stripped there) would crash the same way. **Sales Settings is the exact page this project's own ticket-size work depends on operators filling in** (`dealSize`, product pricing — see issue #79), so this was a real, currently-live defect in this repo's own dev workflow, not a hypothetical. Fixed identically in both files (capture the event value into a local `const` first) and verified via headless Chromium that typing into Sales Settings' company-name field no longer crashes. A repo-wide grep confirms zero remaining instances of the unsafe shape; the visually-similar (but safe) `onChange={(e) => updateX(i, e.currentTarget.value)}` pattern in `app/battlecards/[brand]/battlecards-client.tsx` and `app/salessettings/[client]/sales-settings-client.tsx`'s `updateProduct` calls extracts the value synchronously as a function argument before any state update, so it was never at risk.

`lib/contact-freshness.ts` (`isContactStale`, `staleContactRatio`, `DEFAULT_STALENESS_THRESHOLD_DAYS = 180`, overridable via `CONTACT_STALENESS_THRESHOLD_DAYS`) is a pure module — no React/Mongo/internal `Date.now()`, mirroring `lib/stale-deal.ts`'s shape — computing staleness at read time from `lastVerifiedAt`; missing `lastVerifiedAt` is treated as stale (an honest "unknown," not a fabricated "fresh at creation"), and a future timestamp (clock skew) is treated as not-stale. `app/detail.tsx`'s CONTACTS block renders a "Needs re-verification" badge per stale contact and a stale-count summary ("N of M contacts need re-verification") — GDS's `AdminModal`/`AdminDetailDrawer` `actions` prop has no per-action description slot, so the summary can't render literally under the `REQUEST_REFRESH` button; it's placed next to the contact data it describes instead, without changing that button's own behavior.

**MX-based email verification (2.4.50, issue #67):** `lastVerifiedAt`/staleness above answers "was this contact re-confirmed by a human/agent recently" — it says nothing about whether the email address itself can actually receive mail. `lib/email-verification.ts`'s `verifyEmail()` proves only *domain-level* deliverability via a Node `dns.promises.Resolver` MX lookup (RFC 5321 §5 A-record fallback when a domain has no MX), never a specific mailbox — a catch-all domain always verifies, and a typo'd local part at a real domain is indistinguishable from a correct one under this check; UI/docs copy always says "domain," never "email." Status tiers: `mx-verified` (domain can receive mail), `mx-failed` (confirmed NXDOMAIN or no MX + no A — definitive, never retried), `check-error` (a transient failure — timeout/SERVFAIL/etc. — retried up to twice with 1s/3s backoff before giving up), `unverified` (either not yet checked, or the email failed `lib/validate-lead.ts`'s `EMAIL_RE` format check — MX lookup is never attempted for a malformed address; both cases render identically as "Checking…" per the UI states below, since only the format-invalid case is truly terminal and that's rare enough not to warrant a fifth display state). `isRoleAccount`/`isFreeProvider` flags (checked against small static lists) travel alongside the status but aren't currently surfaced in the UI.

The check runs **asynchronously, never inline** in the request path — `app/lib/email-verification-store.ts`'s `verifyLeadContactsAsync()` is invoked with `void` (fire-and-forget) after `POST /api/leads`'s insert and after `PUT /api/leads/[id]`'s update, so a DNS timeout or resolver outage can never delay or fail a lead write; results land later via a positional `$` `updateOne` once each domain's lookup completes. Contacts sharing a domain are deduped to one DNS lookup, not one per contact. `PUT` only re-checks emails that are new or changed versus what was already stored (diffed against `existing.contacts`), not every contact on every save. `app/detail.tsx`'s CONTACTS block renders a `StatusBadge` next to `contact.email` for each of the four states — always paired with distinct text, never color alone (CLAUDE.md Rule 7) — with a full-context `aria-label` on each.

**Job-title/seniority normalization (2.4.50, issue #68):** `lib/title-normalization.ts`'s `normalizeTitle()` is explicitly rule-based — an ordered regex/keyword lookup table, never ML, no hosted model, no training data — mapping the free-text `contacts[].title` to two derived, persisted fields: `seniorityTier` (`'C-level'|'VP'|'Director'|'Manager'|'IC'|'Unknown'`) and `department` (`'Sales'|'Marketing'|'Operations'|'Executive'|'Unknown'`). Computed inside `lib/contacts.ts`'s `normalizeContact()` — the one shared normalization path every write already funnels through — so it applies identically and automatically to `POST`, `PUT`, and `PATCH ... MODIFY`, with no new call site. Unlike `emailVerificationStatus` (server-computed, passed through unchanged), `seniorityTier`/`department` are **re-derived from `title` every time**, never trusted from an input payload — a caller can't spoof them by sending a fabricated value.

Seniority is checked in fixed, most-senior-first precedence (`C-level > VP > Director > Manager`); a title with no matching rank keyword resolves to `IC` only when its department independently resolved to something recognized (Sales/Marketing/Operations) — a bare `Owner`/`Founder`/`president` signal (Executive department) or a title with no recognizable keywords at all (e.g. non-Latin-script text) resolves to `Unknown` tier instead of guessing `IC`, since neither actually signals org-chart rank. Department resolution reconciles two real inconsistencies in the original spec, both intentional and documented in the module itself: `revenue` was added to the Sales keyword list (absent from the spec's own pseudocode, but required to make its own worked example — "Chief Revenue Officer" → Sales — actually true); the bare `president` keyword excludes `vice president` via a negative lookbehind (without it, "Vice President, Sales" would incorrectly resolve to Executive department instead of Sales, since `president` is a literal substring of `vice president`).

`app/detail.tsx`'s CONTACTS block renders a tier `Badge` and a department `Badge` next to `contact.title`, each hidden individually when its value is `Unknown` — no empty-state chrome, matching this file's existing convention (e.g. the `isDecisionMaker` badge). `scripts/backfill-title-normalization.ts` (importing `lib/backfill-title-normalization.ts`'s pure collection-scan logic, mirroring `scripts/migrate-decision-maker-to-contacts.ts`'s `--dry-run`/`--apply` shape exactly) backfills existing documents written before this feature existed — idempotent, safe to re-run, a contact whose stored values already match the current keyword table's output is left untouched. **Not run against production**: this sandbox has no `MONGODB_URI` (same documented gap as every other Mongo-integration path in this repo) — the script was sanity-checked locally (confirmed it parses, connects to the missing-env-var error path correctly) but a real dry-run against live data is disclosed, real follow-up work for an environment with DB access, not claimed as already done.

**Tech-stack scan (2.4.52, issue #69):** unlike the two fields above, `techSignals`/`techSignalsScannedAt`/`techSignalsScanStatus` are **top-level `Lead` fields, not per-contact fields** — they describe the company's homepage, not any individual person. `lib/tech-stack-scan.ts`'s `scanTechStack()` fetches the lead's own `url` and pattern-matches the HTML against a small signature table (CMS meta generators, analytics/tag-manager snippets, JS framework bundle hints); see `docs/STACK_AND_DEPENDENCIES.md`'s "Outbound Requests / SSRF Guard" section for the full guard chain, since this is the app's first outbound fetch to an arbitrary, attacker-influenced host. `app/lib/tech-stack-scan-store.ts`'s `scanLeadTechStackAsync()` runs the scan and writes the result back; invoked with `void` (fire-and-forget) after `POST /api/leads`'s insert and response are already built, and on-demand via a new `RESCAN_TECH` PATCH action (`app/lib/lead-actions.ts`) that re-scans the lead's own stored `url` — awaited synchronously in that path, since it's an explicit user-triggered action expecting an immediate result, unlike the POST-time scan. `techSignalsScanStatus` is one of `'ok'|'blocked'|'timeout'|'invalid_url'|'non_html'|'error'`; `techSignals` is only ever non-empty when status is `'ok'`. `app/detail.tsx` renders a badge list (found signals), a dimmed "No tech signals detected." (ok, empty), or a dimmed "Scan unavailable" (any other status) adjacent to the country/region/quality badge row — the section is omitted entirely when `techSignalsScanStatus` is undefined (never scanned).

**Ticket-size estimation (2.4.53, issue #79):** replaces trusting the free-written `estimated_annual_revenue_usd`/`pricingByCompany` fields directly (previously zero validation anywhere — capable of producing an $8,000,000,000 estimate for a mid-market lead) with a deterministic, firmographic-based `ticketSizeEstimate` computed server-side on every `POST`/`PUT`. `lib/ticket-size.ts`'s `estimateTicketSize()` is a pure function tried in method-priority order: **`per_unit`** — a brand's `company_settings` (`app/lib/sales-settings.ts`) product line priced for the lead's `size` tier, multiplied by an agent-supplied unit-count signal (`estimated_participants`) and a fixed per-tier volume-discount factor (Enterprise pays less per unit than Small, mirroring real per-seat pricing); **`tier_band`** — the brand's own configured `dealSize` band (`small`/`medium`/`large`/`enterprise`) for that tier; **`unconfigured`** — an honest "not yet set up" result when neither exists, never a fabricated number (mirrors `lib/tech-stack-scan.ts`'s never-fabricate contract). Every computed estimate is a `{low, expected, high, method, confidence}` band, never a bare point value, and is hard-capped at 2× `dealSize.largestWon` when that's configured — the direct, structural fix for the reported bug: once an operator sets a realistic largest-deal-ever-won figure, no estimate for any lead can exceed twice it, regardless of what an upstream agent free-wrote. `DealSize` gained an `enterprise` band alongside `small`/`medium`/`large`, closing a real pre-existing mismatch (`Lead.size` has always had 4 tiers, the interface only defined 3). `app/lib/ticket-size-store.ts`'s `computeTicketSizeForLead()` does the one `company_settings` lookup and calls the pure function; invoked **synchronously** (not fire-and-forget, unlike the tech-stack scan) since this is in-process computation against already-fetched data, not an outbound network call. `app/constants.ts`'s `getTicketSize()` now reads `ticketSizeEstimate` first, falling back to the legacy direct-value display only for a lead written before this shipped (until issue #81's backfill catches it up) — and even that legacy fallback is now shown with an "Unverified estimate" qualifier rather than as a bare trusted figure, per CLAUDE.md Rule 7. `estimated_annual_revenue_usd`, `estimated_participants`, `recommended_tier`, `revenue_model`, and `pricingByCompany` are all kept as-is (agent-supplied signals/audit trail — `estimated_participants`/`revenue_model`/`recommended_tier` now feed the new engine as real inputs; `estimated_annual_revenue_usd`/`pricingByCompany` are no longer trusted as the displayed ticket size but remain stored for reference).

**Backfill (2.4.54, issue #81):** `lib/backfill-ticket-size.ts`'s `backfillTicketSizeCollection()` scans a brand's whole collection and computes/writes `ticketSizeEstimate` for every lead written before issue #79 shipped — idempotent (a lead whose stored estimate already matches what `estimateTicketSize()` derives today, compared on `method`+`expected`, not `computedAt`, is left untouched) and safe to re-run any time `company_settings` changes ahead of issue #82's automated recalculation. Two ways to run it: `scripts/backfill-ticket-size.ts` (CLI, `--dry-run`/`--apply`/`--brand=`, mirrors every prior backfill script in this repo) and `POST /api/admin/ticket-size-backfill` (`x-api-key` guarded, `{brand?, tenantId?, apply?}` body, defaults to dry-run) — the latter added specifically because the repo owner has no terminal/CLI access (mobile-only, per CLAUDE.md) and needs a path they can actually trigger themselves.

**Recalculation (2.4.56, issue #82):** `ticketSizeEstimate` is computed at write time from a snapshot of `company_settings` — if an operator later edits Sales Settings, or a lead's `size` changes, the stored estimate would otherwise silently go stale until that specific lead happens to be re-saved. Two complementary triggers keep it current: a weekly Vercel Cron sweep (`GET/POST /api/admin/ticket-size-recalc`, see `docs/STACK_AND_DEPENDENCIES.md`'s "Hosting and Delivery") recomputes every lead in every brand, and two narrower, faster change-triggers avoid waiting up to a week for an obvious correction — `PUT /api/sales-settings/[brand]`'s save handler fires a `void`, fire-and-forget recompute across that brand's whole collection immediately after a successful save (never awaited, so a slow recompute over many leads can't delay the save's response, the same non-blocking contract already established for issues #67/#69), and `PATCH ... MODIFY` (`app/lib/lead-actions.ts`) recomputes a single lead's estimate inline, synchronously, whenever its `size` field actually changes in that request (cheap, in-process, no reason to defer). All three triggers call the same underlying `computeTicketSizeForLead()`/`backfillTicketSizeCollection()` functions from issues #79/#81 — no duplicated recomputation logic anywhere.

**Calibration (2.4.57, issue #83):** #79's engine ships with deliberately simple, fixed placeholder assumptions (a flat ±50%/±30% band width, a hand-set volume-discount curve by size tier) because there was zero historical data to calibrate against at launch. This closes that loop — the same closed-loop calibration pattern already implemented once for win-rate-by-stage forecasting (issue #56, `lib/win-rate-calibration.ts`), applied to ticket size. A new top-level `Lead.actualDealValueUsd` (always USD, for cross-brand comparability) captures the real, closed contract value — set via a small, standalone capture UI in `app/detail.tsx`, shown only when `kanbanColumn === 'WON'` (deliberately not routed through `handleModify()`, which exists in that file but isn't currently wired to any button — a pre-existing gap, out of scope here). `lib/ticket-size-calibration.ts`'s `computeTicketSizeCalibration()` is a pure function: for every `WON` lead with both a usable `ticketSizeEstimate` and `actualDealValueUsd`, it computes signed mean/median absolute and percent error, grouped by size tier and by method (`tier_band`/`per_unit`), gated on a minimum sample size (`confidence: 'ok'|'insufficient'`) — a `WON` lead with no usable estimate, or with an estimate but no captured actual, is excluded from the math but counted separately (`wonWithoutEstimate`/`wonWithoutActual`), so an operator can see how much of the closed pipeline this affects. `app/lib/ticket-size-calibration-store.ts` persists the result in a `ticket_size_calibration` collection with the same `>24h` staleness/lazy-recompute contract as `app/lib/win-rate-store.ts`, read via `GET /api/ticket-size-calibration`. A "Ticket-Size Calibration" panel on `/forecast` surfaces sample size, mean/median bias (positive = the model underestimates that group, negative = overestimates), and confidence per tier/method — the actionable read is "if this group is confidently biased, adjust that tier's `dealSize` band in Sales Settings by roughly that percentage."

**Manual override (2.4.61, issue #86):** A rep's direct knowledge of a specific deal (a verbal budget number, a comparable recent close) may beat the firmographic model — this resolved the three Open Questions the issue shipped with: (1) an override permanently exempts the lead from every automated recompute — `lib/backfill-ticket-size.ts`'s `backfillTicketSizeCollection()` (the shared function behind the weekly cron sweep, the Sales-Settings-save trigger, and the CLI/admin backfill endpoint) skips any doc whose `ticketSizeEstimate.method === 'manual_override'` in one place, and both `PUT /api/leads/[id]` and `MODIFY`'s own size-change recompute carry the identical guard; (2) a reason is required, mirroring `DECLINE`'s own required `declineReason` — a `MODIFY` request with an override value but no reason is silently ignored, never applied without one; (3) it lives in the #88 "Lead Details" edit form as two new fields (override value + reason) plus a "Clear existing override" button, rather than a separate UI surface. `lib/ticket-size.ts` gains `TicketSizeMethod`'s `'manual_override'` value and `createManualTicketSizeOverride()` — deliberately **not** run through `applySanityCap()`: the cap exists to catch an unvalidated, agent-written figure, while a manual override is the opposite, an explicit reason-required human judgment call, the same trust level CLAUDE.md Rule 7 already extends to a real user action. `low`/`high` both equal `expected` since this is a specific figure, not a modeled band. `app/lib/lead-actions.ts`'s `MODIFY` handler gains `manualTicketSizeExpected`/`manualTicketSizeReason` (set) and `clearManualTicketSizeOverride` (revert to the modeled estimate immediately) — both logged to the existing `outcomelogs` audit trail (`beforeState`/`afterState.ticketSizeMethod`, a distinct `outcomeValue`), reusing the audit mechanism already in place rather than a new collection. `lib/ticket-size-calibration.ts`'s existing method allow-list (`tier_band`/`per_unit` only) already excludes `manual_override` from calibration math by construction — a human's judgment call is not a "the model was right/wrong" data point, so it's counted in `wonWithoutEstimate` rather than skewing a tier/method's bias stats. The kanban card caption and detail-drawer section both render "Manually overridden" rather than "Modelled estimate" once set, per Rule 7.

**Forecast integration (2.4.59, issue #85):** #79 through #83 built and calibrated `ticketSizeEstimate` but the CogMap forecast (`app/lib/forecast.ts`'s `computeForecast()`) kept summing the raw, unvalidated `estimated_annual_revenue_usd` field directly — the exact field #79 exists to stop trusting, left in place in the one number an operator actually reads for planning. All four CogMap aggregations (`pipelineForecast`'s per-column revenue, `revenueByModel`'s per-model revenue, `totalRevenue`'s grand total, and `perLeadValues`'s per-lead value used for concentration-risk ranking) now read a shared `REVENUE_EXPR` Mongo expression — `{$ifNull: ['$ticketSizeEstimate.expected', {$ifNull: ['$estimated_annual_revenue_usd', 0]}]}` — the same legacy-fallback contract `app/constants.ts`'s `getTicketSize()` already established for the lead-detail UI (issue #79/#80), so the forecast and the drawer never disagree about which number is authoritative for a given lead. A lead backfilled by issue #81 or recomputed by issue #82 contributes its capped, sanity-checked `expected` value; a lead somehow still missing an estimate (a gap issue #81/#82 are meant to close to zero) falls back to the legacy field rather than silently contributing 0. Deliberately a value swap only, not a confidence-weighted one: an `expected` figure already sits at the model's central estimate, and folding `confidence`/`low`/`high` into the forecast weighting too would double-count risk the pipeline-stage close-probability weighting (issue #56) already prices in — revisit only once issue #83's calibration data shows a specific confidence tier is systematically mis-weighted, not preemptively. Seyu's forecast is unchanged and out of scope: it's built entirely from `pricingByCompany` (a fully separate per-company pricing model `computeTicketSizeForLead()` was never wired to represent), not from `estimated_annual_revenue_usd`, so there is no legacy field here for `ticketSizeEstimate` to supersede.

**Region multipliers (2.4.60, issue #84):** #79's engine segments purely on `Lead.size`; region — a very different market-size signal across CogMap's NA/CEE/MENA and Seyu's own regions — played no role. `Lead.region` is genuinely free text at the API boundary (confirmed by research before implementing, per CLAUDE.md Rule 5: `lib/validate-lead.ts` has no region enum; `app/lib/normalize-lead.ts` just uppercases whatever string is given, defaulting to `'NA'` when absent; real seed values are only `CEE`/`MENA`, `US` is never actually written), so this ships as a sparse, operator-populated adjustment rather than a fixed enum lookup. `lib/ticket-size.ts`'s `estimateTicketSize()` gains an optional `regionMultiplier` on `TicketSizeInputs`, applied to the raw tier_band/per_unit value **before** the sanity cap (so a region multiplier can shrink or grow an estimate but can never let it escape the existing 2x-`largestWon` ceiling) — absent, non-finite, or `<=0` collapses to a `1.0` no-op, never an error or a zeroed-out estimate. `SalesSettings` gains `regionMultipliers: Record<string, number>` (new "Region Multipliers" section on `/salessettings/[client]`, a repeatable region/multiplier row editor since region has no fixed set of values to render as a form) with a dedicated sanitizer that uppercases keys (matching `normalize-lead.ts`'s own convention) and silently drops zero/negative/non-numeric entries rather than storing a corrupted value. `app/lib/ticket-size-store.ts`'s `computeTicketSizeForLead()` and `lib/backfill-ticket-size.ts`'s `backfillTicketSizeCollection()` both look the lead's own (uppercased) region up in this map and pass the result through — threaded into every existing call site (`POST`/`PUT /api/leads`, `MODIFY`'s size-change recompute, the backfill/recalc sweep) with no new call sites, so a lead's estimate incorporates region the same way at write time, on recalculation (issue #82), and on backfill (issue #81). Deliberately shipped as a mechanism only, not a data-derived heuristic: since the multiplier is operator-configured (identical in spirit to `dealSize`'s own bands, which were also operator-set from day one, not data-derived), there's no reason to wait for issue #83's calibration data to accumulate before making the lever available — an operator can start with `1.0` (no-op) everywhere and tune from real outcomes as they close.

**Unreliable size-tier data defaults to the smallest configured band (2.4.89, issue #111):** Before this, any lead with no `size` value, or one that didn't exactly match `Small`/`Medium`/`Large`/`Enterprise` (free text, wrong case — a real, common state confirmed by scanning production data: 61 CogMap + 104 Seyu leads), returned `method: 'unconfigured'` outright — no ticket size shown at all, even though the brand's `dealSize` was otherwise fully configured. Owner-requested: calculate the smallest realistic figure instead of nothing. `estimateTicketSize()` now, when `sizeTier` is missing, takes whichever `dealSize` band (`small`/`medium`/`large`/`enterprise`) is numerically smallest among whatever the brand has configured — **not** necessarily `small` itself, if a brand's bands happen to be non-monotonic — still through the same sanity cap, region multiplier, and low/high range factors as a real `tier_band` estimate, always `confidence: 'low'`, and flagged with a new `sizeAssumed: true` so callers can tell this apart from a real per-lead estimate. Only falls through to `unconfigured` when the brand has configured no `dealSize` band at all.

Deliberately does **not** guess a specific tier (e.g. `'Small'`) and run it through the normal per-tier logic: `per_unit`'s volume-discount table (`VOLUME_DISCOUNT_BY_TIER`) is steeper for *bigger* tiers, so assuming `'Small'` there can compute a **larger** number than assuming `'Enterprise'` would — the opposite of "smallest." Going straight to the minimum configured `dealSize` band sidesteps that inversion entirely and is simpler to reason about.

`app/constants.ts`'s `TicketSizeDisplay`/`getTicketSize()` and `app/types.ts`'s `Lead.ticketSizeEstimate` both thread `sizeAssumed` through. `app/detail.tsx`'s `ticketSizeDetailSection()` swaps the "Modelled estimate from ..." caption for an explicit "Smallest configured deal size — this lead's size isn't set, using the lowest tier as a conservative placeholder" when `sizeAssumed` is set, rather than presenting it as if the model actually knew this lead's size (CLAUDE.md Rule 7). `app/card.tsx`'s compact kanban-card caption does the same ("Smallest tier (size unknown)" instead of "Modelled estimate"). `lib/ticket-size-calibration.ts` needed no change: it already buckets a WON lead whose `size` doesn't match the enum into a synthetic `'Unknown'` tier group (issue #83's own pre-existing design), which structurally already isolates every `sizeAssumed` lead from polluting the real per-tier accuracy stats — confirmed by inspection, not assumed.

**Forecast integration (2.4.59, issue #85):** `app/card.tsx`'s minimal fix from #79 (a compact `~$500K` value + qualifier) is the space-constrained kanban-card treatment; `app/detail.tsx` gets the full treatment via a `ticketSizeDetailSection()` helper placed directly under the ICE Score block (both answer "how are we scoring this deal"). Three UX states, always paired with real text (never color alone, CLAUDE.md Rule 7): an **estimate** shows the `expected` value prominently, the full `low`–`high` range, and an italic "Modelled estimate from company-size tier/per-participant pricing · low/medium/high confidence" caption; **unconfigured** shows a dimmed message pointing the operator at Sales Settings, the actual lever that fixes it; a pre-backfill **legacy** lead shows its old direct value with an explicit "Unverified estimate — predates the firmographic estimation engine, pending recalculation" caption, never as a bare trusted figure. The whole section is omitted (not shown as empty chrome) when `getTicketSize()` returns `null` — a lead with neither a computed estimate nor any legacy field at all.

### Required-Fields-Per-Stage Gating (2.4.79, issue #72)
Leads could previously be dragged (`COLUMN_MOVE`) or pinned (`PIN`, always targets `ENGAGED`) into any user-driven column with zero field-completeness check — only lead *creation* enforced a quality gate. New pure module `lib/stage-gate.ts`'s `checkStageGate(destinationColumn, lead)` hard-blocks a move into `ENGAGED` or `PROPOSAL` (owner-confirmed scope) unless the lead has at least one `contacts[]` entry and a non-empty `value_proposition`. `DISCOVERED`/`QUALIFIED` stay auto-managed (`lib/kanban-column.ts`'s `AUTO_MANAGED_COLUMNS`, score-driven, never user-moved) and are never gated; `WON`/`LOST` are terminal and not gated either (`DECLINE`'s own required `declineReason` already gates the path into `LOST`). No admin bypass — the owner explicitly declined one, since this app has no admin-role concept that would apply to a per-field workflow policy (super-admin only governs org/brand access).

**Contact requirement simplified to "any contact" (2.4.88).** Originally required a `contacts[]` entry specifically flagged `isDecisionMaker: true` — owner feedback: this app doesn't distinguish contact "types" for gating purposes, only one kind of contact requirement should exist. `isDecisionMaker` remains a real flag a contact can carry (still used by `lib/contacts.ts`'s dedup/sort, `app/lib/outreach/routing-rules.ts`, and `lib/next-step-nudge.ts`'s advisory "add a decision-maker" nudge — none of that changed), it's just no longer what this hard gate checks. Any contact, decision-maker-flagged or not, now satisfies the requirement.

`app/lib/lead-actions.ts`'s `executeLeadAction` checks the gate against `normalizedBody` (already `existing` merged with the request `payload`, before either is stored) rather than `existing` alone — a required field supplied in the same `MODIFY`-shaped request that also moves the lead satisfies the gate, not just pre-existing state. On failure, returns the same `{success: false, error, requestId}` shape every other failure path in this function already uses; `formatStageGateError()` produces a directly-usable message (`"Missing required fields for ENGAGED: a contact, a value proposition"`), not a raw field-path list.

Unrelated, separate gate — not affected by this change: `POST /api/leads`'s own creation-time quality gate (`app/api/leads/route.ts`) blocks a very-low ease/confidence lead unless it has a *verified* contact (`bestContactConfidence()` scoring email/phone/LinkedIn completeness, not the `isDecisionMaker` flag). Different mechanism, different field, deliberately untouched.

Fixed a real, unrelated pre-existing bug discovered while wiring this up: `app/kanban.tsx`'s drag failure handler discarded the actual server-provided error entirely (`throw new Error(\`Move failed: ${res.status}\`)` — status code only, response body never read), so this gate's specific, actionable message would have rendered as a generic "Move failed: 400" in the UI. Now parses `data.error` from the response body first, falling back to the status-only message only if the body can't be parsed.

### Near-Duplicate Review Queue (2.4.80, issue #73)
Dedup was exact-fingerprint-only (`lib/fingerprint.ts` — a SHA1 of `url + entity_name + region`, any character-level difference produces a completely different hash). New pure module `lib/near-duplicate.ts`: `similarity()` computes Dice's coefficient over character bigrams (cheap, no new dependency, tolerant of word-order noise — `"Acme Corp"` vs `"Corp Acme"` scores identically); `findCandidatePairs()` evaluates every pairwise combination in a brand's lead set and flags a pair when either the name score clears an 0.82 threshold or the two leads' normalized domains (`www.`/scheme/path stripped) match exactly — domain match is treated as the stronger signal, surfacing a pair even at a low name score. Candidate-pair identity (`leadIdA`/`leadIdB`) is sorted lexicographically so it's stable across scans regardless of MongoDB's undefined `find()` ordering — otherwise a re-scan producing the same pair in reversed order would silently duplicate the review row.

New collection `duplicate_reviews`: `{tenantId, brand, leadIdA, leadIdB, score, matchedOn, status: 'pending'|'dismissed'|'confirmed', createdAt, reviewedAt?, reviewedBy?}`. `POST /api/admin/duplicate-scan` (session-gated, super-admin only) fetches the brand's lead set, runs `findCandidatePairs()`, and inserts only pairs not already present in `duplicate_reviews` under **any** status — so a pair a human already dismissed or confirmed on an earlier scan never resurfaces. `GET/PATCH /api/duplicate-reviews` list pending pairs (joined to both leads' `entity_name`/`url`/`kanbanColumn` for side-by-side display, `(deleted lead)` placeholder if a referenced lead is gone) and record a dismiss/confirm decision.

**Scan cap (2.4.87, issue #107)**: `findCandidatePairs()` is O(n²) — a brand/tenant with tens of thousands of leads would mean tens/hundreds of millions of bigram comparisons in one synchronous request. The scan is now capped at `MAX_SCAN_SIZE = 2000` leads (sorted newest-first via `createdAt desc`, so a truncated scan is deterministic across repeated runs), with `totalAvailable`/`truncated` in the response so a capped scan is visible to the operator instead of silently incomplete — `admin-duplicates-client.tsx` shows a yellow notification calling out the cap when it applies, rather than reporting a scan that looks complete but wasn't. Verified by direct execution against `mongodb-memory-server` (seeded 2500 leads, confirmed `scanned: 2000, totalAvailable: 2500, truncated: true`) rather than through the route handler itself — the route requires a real super-admin session, which (same constraint as every other `requireSuperAdminSession`-gated route in this sandbox — see the SSO section below) can't be fabricated here; only the no-session 401 path is covered by an automated integration test (`tests/integration/admin-session-auth.integration.test.ts`).

**Deliberate deviation from this issue's own original draft**: session-based auth (`requireSuperAdminSession`, matching `/api/admin/users/*`), not the `x-api-key` scheme the draft first proposed — `/admin/duplicates` is a human clicking a "Scan for duplicates" button in a browser, and the browser has no safe way to hold `SLG_API_KEY` (the same "browser can't hold this secret safely" constraint documented for `PUT /api/sales-settings/[brand]` and the win-rate recalc endpoint). Caught during implementation, not assumed from the issue text.

`/admin/duplicates` (new nav entry under the existing super-admin "Admin" section in `app/components/AppNav.tsx`, alongside "Users & Access"): GDS `AdminDataTable` listing pending pairs side-by-side, "Not a duplicate" / "Confirm duplicate" actions. **Dismiss/confirm only — no merge action exists anywhere in this delivery**, per owner-confirmed scope; a real merge (combining contacts/history/scores) is an explicit future issue once this review queue itself proves useful. `PATCH` never re-validates that both referenced leads still exist before allowing a decision — a pair can always be dismissed even if one side was since deleted, since dismissing is harmless (nothing is merged or deleted) and 404ing here would make an already-orphaned review permanently un-dismissable, the opposite of the intended safety property.

## Request and Response Flows

### List Leads
1. Frontend calls `GET /api/leads?brand=<brand>&limit=500` — as of 2.4.7, with `cursor=<nextCursor>` on subsequent requests, looping until `hasMore` is `false` (no more hard-capped single fetch)
2. Route builds tenant-aware filter; legacy docs without `tenantId` are included for `default`
3. Without `cursor`: legacy path, sorts by `kanbanColumn`, `sortOrder`, `createdAt`, paginated via `page`/`skip`. With `cursor`: sorts by `createdAt desc, _id desc` (matching the dedup step's final order below) and paginates via the cursor instead
4. Response dedups by fingerprint client-side and strips top-level contact fields
5. Frontend normalizes and renders kanban or table view

### Create Lead
1. Frontend or agent calls `POST /api/leads?brand=<brand>`
2. `requireApiKey` enforces auth
3. Request body is validated
4. Contact fields and address are normalized
5. Brand-aware pros/cons are normalized
6. Duplicate detection uses fingerprint match across tenant and legacy docs
7. ICE score is calculated from impact, confidence, and ease
8. Quality gate rejects low-confidence/ease leads without verified contact
9. Lead is inserted with `sortOrder = count * 100`
10. Outcome log records creation

### Action Lead
1. Frontend calls `PATCH /api/leads?brand=<brand>&id=<id>` with action payload
2. `requireApiKey` enforces auth
3. `executeLeadAction` loads lead, validates patch, applies action-specific updates
4. Supported actions: ACCEPT, DECLINE, MODIFY, PIN, REQUEST_REFRESH, COLUMN_MOVE
5. Outcome log records mutation with before/after state
6. Response returns normalized lead

### Update Lead
1. Frontend or agent calls `PUT /api/leads/[id]?brand=<brand>` with field updates
2. `requireApiKey` enforces auth
3. Request body is validated via `validateLeadPayload(body, brand, { partial: true })` — the same rules `POST` enforces (URL format, ICE range, forbidden cross-brand vocabulary), but only for whichever fields are actually present in the partial update, not required unconditionally
4. Route updates allowed fields without requiring the ACCEPT/DECLINE/etc. action workflow
5. **Auto-reclassification (2.4.4):** if the update includes `ice` and does *not* also explicitly include `kanbanColumn`, and the lead's current `kanbanColumn` is `DISCOVERED` or `QUALIFIED` (`isAutoManagedColumn()`), the route recomputes the ICE score from the new `ice` values and sets `kanbanColumn = deriveKanbanColumn(newIceScore)`. A lead that has been moved to `ENGAGED`/`PROPOSAL`/`WON`/`LOST` (by drag-and-drop or an action) is never auto-moved again regardless of later score changes.
6. **`ice` is coerced to real numbers before storing (2.4.8):** unlike `POST` (which runs the whole body through `normalizeLead()`'s `ensureNumber()`), this route previously copied `body.ice` verbatim — `validateLeadPayload` only range-checks it via `Number()`, it never mutates the stored value. A request with numerically valid but string-typed ICE fields would pass validation yet persist as strings, which then broke the sort aggregation below (`$multiply` throws on a string operand). Fixed to match `POST`'s guarantee.
7. Response returns updated lead

### Kanban Column Chunk (auto-classification and sort rule, 2.4.4)
`GET /api/leads/columns?column=<COLUMN>` is the kanban board's sole read path (cursor-paginated, `CHUNK_SIZE = 50`) — sorting happens entirely in this server-side aggregation, never client-side; the frontend renders whatever order the response returns. Its sort behavior branches by column:
- **`DISCOVERED`** (ICE < 500) and **`QUALIFIED`** (ICE ≥ 500) are auto-managed: leads are placed here purely by computed ICE score, and the column always sorts high → low by that score. There is no stored, denormalized sort field for these two columns — the route runs an aggregation pipeline (`$addFields` using `ICE_SCORE_AGGREGATION_EXPR`, then `$sort: { _iceScore: -1, _id: -1 }`), and cursor pagination is encoded as `<iceScore>|<id>` instead of `sortOrder`. As of 2.4.8, the expression reads each ICE field via `$convert` (`to: 'double'`, safe `onError`/`onNull` fallback to 0) rather than a bare `$multiply` on the raw stored value — this recovers the real number from an already-corrupted numeric-string field instead of throwing and failing the whole column fetch.
- **`ENGAGED`, `PROPOSAL`, `WON`, `LOST`** remain exclusively user-managed: unchanged `sortOrder`-based sort (`{ sortOrder: -1, createdAt: -1 }`), cursor encoded as `<sortOrder>|<id>`. A lead only reaches one of these columns via an explicit action (drag-and-drop `COLUMN_MOVE`, `ACCEPT`, `PIN`, etc.) and is never auto-moved out of it by a score change.

Placement rule: a lead moves between `DISCOVERED`/`QUALIFIED` automatically whenever its `ice` score is updated (see "Update Lead" above) or at creation (`deriveKanbanColumn` in `POST /api/leads`). Moving a card out to any of the 4 manual columns (drag-and-drop or an action) changes `kanbanColumn` explicitly, which permanently opts that lead out of auto-classification.

### Outreach
1. Frontend posts to `/api/outreach-logs` with lead context and channel
2. Routing rules evaluate channel eligibility
3. If allowed, log is persisted with routing metadata
4. Analytics endpoint aggregates logs by template and channel

## Auth, Middleware, CORS, and Security

### Middleware
- Matches `/api/:path*`
- Sets CORS headers for allowed origins
- Sets security headers: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`
- Handles OPTIONS preflight

### API Key Auth
- `requireApiKey` guards write and **admin-only** endpoints — the external research agent's writes (`POST /api/leads`, `PUT /api/leads/[id]`) and every `/api/admin/*` route
- Key is passed via `x-api-key` header
- When `SLG_API_KEY` is set, a request is rejected (401) unless it sends the exact matching header — a missing header is rejected identically to a wrong one. When `SLG_API_KEY` is unset entirely, all requests are allowed through (documented fail-open behavior for local/dev use) — `requireApiKey` itself, used standalone on `POST`/admin routes
- **`PATCH /api/leads` and `DELETE /api/leads/[id]` are deliberately NOT guarded by `requireApiKey`** (fixed in 2.4.65, issue #91) — these are the browser's own lead-action/delete write paths (Accept/Decline/Pin/Refresh/Move/Modify via `app/kanban.tsx`, `app/detail.tsx`, `app/sales/[brand]/sales-page-client.tsx`), which never sent an `x-api-key` header, same "browser can't hold this secret safely" reasoning as `PUT /api/sales-settings/[brand]` above. Once `SLG_API_KEY` was actually configured in production, every action from the real app was silently returning 401 — found and verified live against production while investigating issue #91 (a real column-move PATCH, and the app's own read of `handleAction`/`handleMove`, confirmed neither ever sent the header). This was compounded by a second, independent bug found in the same investigation: `<Notifications />` (`@mantine/notifications`) was never mounted anywhere in this app, so every `showNotification()` call across the whole app (success and failure alike) had been a silent no-op — fixed by mounting it in `app/components/Providers.tsx`. As of 2.4.86/issue #104, this route (and every other core lead route) is gated instead by `requireBrandAccessApi` — see below.

### Security Audit Fixes (2.4.85)

A comprehensive code audit (security, correctness, code quality — three parallel passes, each finding independently cross-verified rather than trusted at face value) surfaced several real, confirmed issues, fixed in this release:

**`GET`/`PUT /api/prompts` and `GET`/`PUT /api/admin/toggle` had no authentication at all.** Both routes were merged in from unrelated work (the tenant-prompt-editor and per-tenant discovery/enrichment-toggle admin features) without ever adopting this app's session-auth pattern — confirmed by reading the actual route code, not assumed from the surrounding UI. `/api/prompts` reads/writes the autonomous research agent's discovery/enrichment prompt content (`prompts` MongoDB collection plus a disk mirror the cron generator reads directly); `/api/admin/toggle` flips per-tenant automation on/off (`tenant_operations` collection plus the same `Agents/contentcreator/tenants.json` file). Both now call `requireSuperAdminSession()` first in every handler, the same pattern `/api/admin/users` and `/api/admin/duplicate-scan` already use — session-based, not `x-api-key`, since both are exclusively browser-called from `/admin/prompts/[brand]`'s own client component. `app/admin/prompts/[brand]/page.tsx` itself had the same gap (no page-level redirect gate at all, unlike its sibling `/admin/users`/`/admin/duplicates` pages) — fixed identically.

**Unauthenticated path-traversal arbitrary file write, `/api/prompts`.** `resolvePromptPath()` interpolated the request's `tenantId` directly into a filesystem path with no sanitization — confirmed exploitable: `path.join(PROMPTS_DIR, 'discovery', '../../../../../../tmp/pwned.md')` resolves clean out of the intended directory, verified by direct execution before the fix. New `lib/safe-identifier.ts`'s `isSafeIdentifier()` (a plain `[a-zA-Z0-9_-]+` allowlist, not a blocklist of `..`/`/` — allowlisting is the only pattern that can't be bypassed by an encoding this repo didn't think to blocklist) is checked before either `GET` or `PUT` touches the filesystem, returning 400 on rejection. Extracted to its own module rather than exported from the route file itself — Next's route-file type validation only permits recognized handler exports (`GET`/`POST`/etc.), so a route-file export of a plain helper function fails the generated route-type check.

**`lib/validate-lead.ts`'s `validatePatchPayload` MODIFY branch called `validateLeadPayload` without `{ partial: true }`** (unlike `PUT /api/leads/[id]`, which correctly passes it) — a real, currently-shipping bug, not introduced this session. Every real MODIFY payload the app sends (`app/detail.tsx`'s `handleModify`/`handleSaveActualDealValue`/`handleClearTicketSizeOverride`) omits `country`/`kanbanColumn`/`ice` (an edit to some fields isn't a re-creation of the whole lead), so `validateLeadPayload`'s create-mode required-field checks rejected all of them — confirmed by running the actual payload shapes through the real function before and after the fix. **Practical impact this was causing in production**: Edit Lead Details save, actual-deal-value capture (issue #83's calibration input), and the manual ticket-size-override clear (issue #86) all 400'd unconditionally. One-line fix (`{ partial: true }`), 4 new regression tests covering the exact previously-failing payload shapes.

**`lib/quality-registry.ts`'s `enforceQualityCeiling` could write a garbage string into the `qualityStatus` enum field.** `hierarchy.indexOf(current)` returned `-1` for any unrecognized status string, which the reduce's `currentIndex < lowestIndex` comparison then treated as *lower than every real status* — so a single malformed entry in the client-controlled `upstreamQualityStatuses` array became the computed "ceiling," and that literal garbage string got returned and written to the lead's `qualityStatus` field. Confirmed reachable via `app/lib/lead-actions.ts`'s `MODIFY` branch, which passes the field through with no validation anywhere in `lib/validate-lead.ts`. This path was latent (blocked by the MODIFY validation bug above rejecting the request first) — fixing that bug without also fixing this one would have reactivated live data corruption. Fixed by allowlist-filtering both `proposedStatus` and every `upstreamStatuses` entry against the known hierarchy before any comparison; an unrecognized `proposedStatus` now falls back to `'DRAFT'` (the same safe default already used for a missing one), and unrecognized upstream entries are dropped rather than corrupting the ceiling calculation. 8 new unit tests, including one asserting the function can never return a value outside `DRAFT`/`CHECKED`/`VERIFIED` for any input.

**Findings deliberately not fixed in this release** (real, but each needs its own scoped follow-up, not a rushed fix bundled into a security-audit commit): `GET`/`PATCH /api/leads`, `GET /api/leads/columns`, `PATCH /api/leads/bulk`, and `DELETE /api/leads/[id]` had no authentication of any kind at the time this section was first written — since fixed in 2.4.86, issue #104 (see below). The remaining six deferred findings (`requireApiKey`'s fail-open behavior, the `GET /api/search` regex, `lib/near-duplicate.ts`'s scan cap, `executeLeadAction`'s counters, bulk `leadIds` dedup, and the duplicated tenant-filter helpers) were fixed in 2.4.87, issues #105-#110 — see below.

### Prompt Editor and Per-Tenant Automation Toggle

Two admin-only features referenced above only as a security-fix footnote — here's what they actually do, as a product feature, for the first time in this file.

`/admin/prompts/[brand]` (`app/admin/prompts/[brand]/page.tsx`, server-gated identically to `/admin/users`/`/admin/duplicates` — non-super-admin redirects before rendering anything) lets a super admin view and edit the free-text instructions ("prompts") that drive the external OpenClaw/KiloClaw research agent's own Discovery (finding new leads) and Enrichment (adding detail to existing leads) behavior for a given `{brand, tenantId}` — two separate tabs, one per operation. `GET`/`PUT /api/prompts` (`prompts` MongoDB collection, plus a disk mirror at a path the cron generator reads directly — so a saved edit takes effect on the agent's *next* run, not instantly) back the read/save. Editing and saving this text is a real, direct lever on the agent's future behavior, not documentation of it.

Each tab also renders an **Enabled** switch — a separate control from saving prompt text, backed by `GET`/`PUT /api/admin/toggle` (the `tenant_operations` collection, plus a best-effort write to the same cron generator's `Agents/contentcreator/tenants.json` file so the change takes effect immediately rather than waiting for that file to be regenerated some other way; a failed file write is silently ignored since Mongo remains the source of truth on the next read). Flipping it turns Discovery or Enrichment on/off for that tenant. The client optimistically flips the switch, then reverts it and shows an error if the `PUT` fails — never leaving a false "on" displayed against a save that didn't actually happen (CLAUDE.md Rule 7).

Both `/api/prompts` and `/api/admin/toggle` are session-gated (`requireSuperAdminSession()`), not `x-api-key` — this is exclusively a human clicking Save/toggle in a browser from `/admin/prompts/[brand]`'s own client component, the same "browser can't hold `SLG_API_KEY` safely" reasoning documented throughout this file for every other browser-originated write.

### Remaining Deferred-Finding Fixes (2.4.87, issues #105-#110)

Six smaller findings from the same 2.4.85 audit, each independently scoped and tracked as its own issue per this repo's own workflow rule, fixed together in one release:

- **`requireApiKey` fail-open when `SLG_API_KEY` is unset (issue #105).** Previously granted access unconditionally in every environment when the key wasn't configured — intentional for local/dev, but a real risk if a production deploy ever loses the env var. Now fails closed (401) specifically when `process.env.NODE_ENV === 'production'`; dev/test behavior (fail open) is unchanged. `requireCronOrApiKey` inherits the same behavior via its own `requireApiKey` fallback.
- **Unescaped `$regex` in `GET /api/search` (issue #106).** `buildSearchFilter()`'s six `$regex` clauses interpolated the raw `q` parameter with no escaping — a ReDoS risk against Mongo's regex engine and a functional bug (a literal search containing `.`/`*` matched far more than intended). Now runs `q` through the existing `escapeRegExp()` (`app/lib/search/tagged-content-filter.ts`), the same helper `GET /api/leads`/`GET /api/leads/columns` already use for their own regex-matched fields.
- **`lib/near-duplicate.ts`'s uncapped O(n²) scan (issue #107).** See the Near-Duplicate Review Queue section above for detail — capped at 2000 leads per scan, truncation surfaced in the response and the admin UI.
- **Non-atomic counter increments in `executeLeadAction` (issue #108).** `acceptanceCount`/`declineCount`/`feedbackScore` were computed as `existing.field + 1` in JS then written via a single `$set` — two concurrent ACCEPT/DECLINE calls on the same lead (e.g. a retried tap on a flaky mobile connection) both read the same starting value and both wrote the same result, losing an increment. Now uses Mongo's atomic `$inc` (combined with the existing `$set` in the same `findOneAndUpdate` call — Mongo permits both operators in one update document), which is correct by construction regardless of interleaving. **Honestly disclosed test gap**: a `Promise.all`-based test firing two concurrent `executeLeadAction` calls against the same lead was written to reproduce the race directly, but it passed identically with the pre-fix code too (both calls appear to serialize through this test harness's single in-process `mongodb-memory-server` connection rather than genuinely racing) — so it wasn't a real regression guard and was removed rather than kept as a test that provides false confidence. The fix's correctness rests on `$inc` being MongoDB's own documented atomic primitive, not on a passing test.
- **`PATCH /api/leads/bulk` not de-duplicating `leadIds` (issue #109).** Combined with the #108 bug above, a duplicated ID in one bulk request double-ran `executeLeadAction` for that lead. `leadIds` is now de-duplicated (stringified, first-seen order) before the 100-lead cap check and the processing loop.
- **`getTenantId`/`tenantFilter` reimplemented locally in 11 route files instead of importing `lib/tenant.ts` (issue #110).** Pure refactor, no behavior change — all 11 now import the shared helpers. `app/api/health/route.ts`'s local `getTenantId` is deliberately left alone: it returns `''` (not `'default'`) when absent, a genuine semantic difference for that route's own optional tenant-scoped health metrics, not duplication.

Full quality gate clean for all six: tsc 0 errors, lint 0 errors/warnings, vitest, smoke, build. See `CHANGELOG.md`'s 2.4.87 entry for exact test counts.

### Core Lead API Access Control (2.4.86, issue #104)

Per-organization access control (2.4.73, issue #103, below) gated every brand-scoped *page*, but the underlying data API those pages' client-side code calls (`GET`/`PATCH /api/leads`, `GET /api/leads/columns`, `PATCH /api/leads/bulk`, `GET`/`DELETE /api/leads/[id]`) had no authentication at all — `GET` routes were "public by original design" (predates SSO), and the write/delete routes had deliberately dropped `requireApiKey` (issue #91, above) with no replacement guard, because a browser can't hold `SLG_API_KEY` safely. The net effect: anyone who knew or guessed a `brand` value could list, modify, bulk-decline, or delete another organization's leads — including contact PII — with no login and no key, which defeated per-org access control's actual guarantee at the one layer that matters, the data itself.

**Fix**: `lib/require-brand-access-api.ts`'s `requireBrandAccessApi(request, brand)` — the Route Handler equivalent of `lib/require-brand-access.ts`'s page-level gate (that one calls `redirect()`, which only works in Server Components). It accepts either: a valid `x-api-key` header matching `SLG_API_KEY` (the machine-caller path — research agent, documented external integrations), or a valid `sso_id_token` session cookie belonging to a user with access to the specific `brand` in the request (the browser path — the cookie is already sent automatically on every same-origin request, no code change needed on the client side). Unlike `requireApiKey`'s own fail-open behavior when `SLG_API_KEY` is unset, the API-key branch here requires the env var to actually be configured or it's skipped entirely, falling through to the session check — an unset key can never silently grant access on this combined-auth path. Mongo not configured fails closed (503), matching `requireBrandAccess`'s own page-level behavior.

Applied to all 6 routes; `GET /api/leads/[id]` (single-lead fetch) is included even though it wasn't separately enumerated in the original 2.4.85 audit note, for the same PII-exposure reason as the list endpoint. `POST /api/leads` and `PUT /api/leads/[id]` are unchanged — those keep their existing separate `requireApiKey` guard (the external research agent's write path, never called from the browser).

**Test coverage**: `tests/lib/require-brand-access-api.test.ts` (the API-key branch and the no-credentials-at-all 401, both testable without a real signed SSO JWT) plus the existing `tests/integration/leads*.integration.test.ts` suite, updated to authenticate via `x-api-key` (`tests/integration/helpers/api-request.ts`) since minting a real JWT isn't possible in this sandbox — same constraint already established for `tests/integration/admin-session-auth.integration.test.ts`. What remains genuinely unverified here, same gap as 2.4.73's own note above: a real authenticated browser session actually being granted access by this new check. The owner should confirm a real logged-in session can still read/act on leads for a brand they have access to, and gets a 403 for one they don't, after this deploys.

`docs/OPERATOR_GUIDE.md`'s `curl` examples and `README.md`'s API Overview are updated to reflect that there is no longer an unauthenticated read path.

### SSO Integration (2.4.71, issue #102, phase 1 — infrastructure only, no page gated yet)
Owner-requested integration of `https://sso.doneisbetter.com` (DoneIsBetter SSO — same team as `@sovereignsquad`'s GDS design system already used throughout this app). Before this, the app had **no login system anywhere** — every page is still anonymously accessible today; only admin-only API routes are gated (`requireApiKey`, above). This phase ships the OAuth plumbing without changing any existing page's access behavior, since which pages (if any) should actually require login is a real architectural decision the owner hasn't made yet — not something to guess at, per CLAUDE.md Rule 5.

**Protocol, verified against the real live service, not assumed:**
- OAuth 2.0 Authorization Code flow + PKCE (S256), OIDC-compliant. `iss`/`jwks_uri`/endpoint paths confirmed by fetching the real `https://sso.doneisbetter.com/.well-known/openid-configuration` and `/.well-known/jwks.json` directly — not taken from their docs prose alone.
- Two-layer permission model: SSO-level `permissionStatus` (`pending`/`approved`/`revoked`, decided by an SSO admin, not this app) and app-level `role` (`user`/`admin`, this app's own to interpret). Their own docs are explicit that ID token claims are identity only — authorization always requires a second, live call to their permissions API; this repo follows that (`lib/sso.ts`'s `getPermission()`), never trusting a cached or token-embedded role for access decisions.
- **A real gap in their own published docs, not silently worked around**: the quickstart requires PKCE as a hard requirement, but their own published React example (`/docs/examples/react`) omits it entirely from both the login redirect and the token exchange. This repo implements PKCE properly per the quickstart's actual requirement (`lib/sso.ts`'s `generateCodeVerifier`/`generateCodeChallenge`, RFC 7636 S256 — verified against the RFC's own Appendix B test vector in `tests/lib/sso.test.ts`, not just "looks about right"), not the incomplete example.
- Their own published example is Pages Router (`pages/api/auth/callback.js`); this repo is Next.js 16 App Router throughout, so every route is a real `app/api/.../route.ts` handler using `NextRequest`/`NextResponse`, not a copy-paste of their snippet.

**Files**: `lib/sso.ts` (PKCE helpers, authorize-URL builder, token exchange/refresh, `jose`-based ID token verification against the live JWKS, permission lookup — all pure/network functions, no React) · `app/api/auth/login/route.ts` (builds the PKCE authorize redirect, sets short-lived `sso_oauth_state`/`sso_code_verifier` HTTP-only cookies) · `app/api/oauth/callback/route.ts` (validates `state`, exchanges the code, verifies the ID token, calls the permissions API, sets session cookies, routes to `/access-pending`/`/access-denied`/`/`) · `app/api/auth/session/route.ts` (validates the session, transparently attempts a refresh on an expired ID token before falling back to 401) · `app/api/auth/logout/route.ts` (clears local cookies, returns their documented `GET /api/oauth/logout` URL for the client to navigate to — their own React example instead calls an undocumented `/api/public/logout`, a real inconsistency between their example and their API reference; this repo follows the documented reference) · `app/components/AuthProvider.tsx`'s `useAuth()` hook (mounted in `app/components/Providers.tsx` as of 2.4.73/issue #103) · `app/access-pending/page.tsx`, `app/access-denied/page.tsx`.

**Real client registered (2.4.72, 2026-07-26)**: owner obtained a real `client_id`/`client_secret` from `sso@doneisbetter.com`, registered with two redirect URIs (`https://salesleadgenerator.vercel.app/auth/callback` and `/api/oauth/callback`), scopes `openid profile email offline_access`. This app's actual callback route was originally built at `app/api/auth/callback/` (phase 1, before the real registration existed) — **moved to `app/api/oauth/callback/route.ts`** to match one of the two registered URIs exactly (chosen over `/auth/callback` for consistency with this app's existing `app/api/*` Route Handler convention, and with the SSO provider's own `/api/oauth/*` endpoint naming). `SSO_REDIRECT_URI` must be set to `https://salesleadgenerator.vercel.app/api/oauth/callback` — the other registered URI (`/auth/callback`) is valid at the SSO provider but unused by this implementation. Real credentials are stored only in this sandbox's gitignored `.env.local` (for local verification) and must be set in Vercel's own Project → Environment Variables for production — this repo has no Vercel API/CLI credentials in this session to do that programmatically, so it's a manual step for whoever has dashboard access.

### Per-Organization Access Control (2.4.73, issue #103)

Owner-requested phase 2, answering issue #102's open scope questions directly: a designated super admin manages which SSO-authenticated users can access which brand (`cogmap`/`seyu`), with what role, and every brand page now actually enforces it — the first real login requirement anywhere in this app.

**Why a new collection, not DoneIsBetter's own permission API**: `GET/PUT/DELETE /api/users/[userId]/apps/[clientId]/permissions` (used already, above) is per-*app* — it answers "can this person use salesleadgenerator at all," never "can they see CogMap vs. Seyu." That distinction is this app's own business logic; DoneIsBetter has no concept of it. `lib/sso-access.ts` owns a new `sso_user_access` collection (`{ssoUserId, email, name, orgAccess: {cogmap?: 'admin'|'user', seyu?: 'admin'|'user'}, createdAt, updatedAt}`), upserted once per successful login (`app/api/oauth/callback/route.ts`, non-blocking — a DB hiccup here never fails an otherwise-successful SSO login) and read on every access decision.

**Super admin status is deliberately not stored** — persisting an `isSuperAdmin: true` field risks drift (a record created while someone was a super admin would stay stamped `true` after their email is removed from the env var). `isSuperAdminEmail()` derives it fresh on every check, comparing the verified ID token's own `email` claim against a comma-separated `SSO_SUPER_ADMIN_EMAILS` env var. A super admin bypasses `orgAccess` entirely and unconditionally for every brand — the deliberate safety net against the sole operator (iOS-mobile-only access to this environment, no other way in) ever getting locked out by a bug in the per-org assignment logic itself.

**Enforcement, not just display**: per CLAUDE.md Rule 7 ("UI affordances must match real capability"), a menu that merely *hides* inaccessible links without the server actually blocking direct URL access would be security theater, not access control. `lib/require-brand-access.ts`'s `requireBrandAccess(brand)` runs at the top of all five brand-specific Server Component pages (`/sales/[brand]`, `/salessettings/[client]`, `/forecast/[brand]`, `/battlecards/[brand]`, `/outreach/templates/[brand]`) before any data fetch: no session → `redirect('/api/auth/login')` (straight to the real SSO login, this app has no login form of its own); session valid but not authorized for that specific brand → `redirect('/access-denied')`. `/admin/users` (below) and its two API routes (`app/api/admin/users/route.ts`, `app/api/admin/users/[userId]/access/route.ts`) use the same pattern via `lib/session.ts`'s `requireSuperAdminSession()` — a distinct, session-based auth scheme from `lib/api-auth.ts`'s `requireApiKey` (machine-to-machine, the external research agent's writes; has no concept of "who is this person").

**Admin UI**: `/admin/users` (`app/admin/users/page.tsx`, server-gated identically to the brand pages, plus the super-admin check — redirects before rendering anything to a non-super-admin) + `admin-users-client.tsx` (GDS `AdminDataTable`, matching this app's established admin-page convention already used by `/battlecards/[brand]` and `/forecast/[brand]`). Lists every user who has ever logged in via SSO, one `Select` per brand (`none`/`user`/`admin`) that `PUT`s `app/api/admin/users/[userId]/access/route.ts` on change. A super admin's own row shows disabled `admin` selects for every brand — their access can't be edited via this UI because it isn't stored here at all.

**Nav (`app/components/AppNav.tsx`)**: mounted `AuthProvider` for the first time (`app/components/Providers.tsx`), driving three real states instead of one URL-derived one — not logged in (a "Sign in" link), logged in with 0 accessible brands (a genuine "no access yet, contact your admin" message, distinct from "not logged in" and from the old "no URL context" fallback it replaces), and 1 vs. 2+ accessible brands. Exactly 1 renders the same per-client section as before. 2+ adds a new organization `Select` above it — the first client picker anywhere in this app (closing the gap 2.4.68's docs called out: "no client picker exists anywhere in this app"). Selecting an org only changes which org's links are *shown*, not an immediate navigation — the user still clicks e.g. Pipeline to actually go there. A super admin always sees an **Admin** section linking to `/admin/users`, regardless of `accessibleBrands` (which, for a super admin, is always every configured brand — see above).

**Real, disclosed verification gap**: every pure access-resolution function (`isSuperAdminEmail`, `getAccessibleBrands`, `hasAccessToBrand`, `getRoleForBrand`) has full unit test coverage (`tests/lib/sso-access.test.ts`), and the DB layer has a real `mongodb-memory-server` integration test (`tests/integration/sso-access.integration.test.ts`). The real-redirect behavior of `requireBrandAccess`/`requireSuperAdminSession` for an **unauthenticated** request was verified against a real running server (`curl`, no cookie — confirmed `/sales/cogmap`, `/admin/users`, `GET /api/admin/users`, and `PUT /api/admin/users/[id]/access` all correctly redirect/401 with no session). The nav's three states were verified via a real Playwright render with `/api/auth/session` route-mocked (including the org switcher actually changing which links are shown). What remains genuinely unverified in this sandbox: a real, **authenticated** request — completing an actual human SSO login and confirming `requireBrandAccess` grants access correctly for a real signed session. No private key exists in this sandbox to fabricate a valid ID token, and no real password/2FA exists to complete a real hosted login. **The owner should personally complete a real login immediately after this deploys**, before relying on it for anything. Reverting via git remains the safety net if something's wrong.

**Critical deployment dependency**: `SSO_SUPER_ADMIN_EMAILS` must be set in Vercel alongside the four `SSO_*` vars from phase 1, or **nobody** — including the owner — can be granted org access after this deploys, since the `/admin/users` UI that grants it is itself gated on being a super admin. This isn't a soft degradation; it's a full app lockout for every user until that one env var is set correctly.

**First-login welcome experience for zero-access users (2.4.74).** Owner-confirmed real login working, then requested: a brand-new user who successfully signs in but hasn't been assigned to any organization yet previously landed on the plain marketing root page (`app/page.tsx`) — context-free for someone who just authenticated. `lib/sso-access.ts`'s `resolveLoginDestination(permissionStatus, email, orgAccess)` (pure, fully unit-tested) is the single decision point `app/api/oauth/callback/route.ts` now calls: DoneIsBetter's own `pending`/`revoked` status is checked first (that gate is theirs, not this app's), and only once that's clear does this app's own zero-brand-access state matter — approved by DoneIsBetter but not yet assigned to CogMap or Seyu here now also routes to `/access-pending`, repurposed with a warmer "Welcome! ... We'll be in touch soon" message (was "Access Pending" / "an SSO administrator hasn't approved..." — that copy was specifically about DoneIsBetter's own gate, which reads as more alarming/opaque than necessary for the much more common "just hasn't been assigned an org yet" case both states now share). A super admin is exempt by construction — `getAccessibleBrands()`'s super-admin bypass means `resolveLoginDestination` never routes them here regardless of `orgAccess`. "Added to the user list" was already correct before this change — `upsertUserSeen()` in the callback route runs unconditionally on every successful login regardless of downstream permission/access status, specifically so a zero-access user already shows up in `/admin/users` ready for the super admin to grant access; verified via a new `resolveLoginDestination` unit-test suite (6 tests) covering every permission/access combination, and a real Playwright screenshot of the redirect target's rendered copy.

**Land on Forecast, not the marketing root, when access exists (2.4.75).** Owner-requested follow-up: a user *with* organization access still landed on `/` (the brand-agnostic marketing page) after login — not useful for someone who just authenticated and has real data to see. `resolveLoginDestination()` now returns `/forecast/${accessibleBrands[0]}` (their first accessible brand's Forecast page) instead of `/` whenever `getAccessibleBrands()` returns at least one brand — `/access-pending`/`/access-denied` for the zero-access/pending/revoked cases are unchanged. "First" needed to be made genuinely deterministic for this to be correct: `getAccessibleBrands()` previously derived brand order from `Object.keys(orgAccess)` — MongoDB's field-insertion order, which depends on the sequence a super admin happened to click through in `/admin/users` and could put `seyu` before `cogmap` for no meaningful reason. Fixed to always iterate `BRAND_CONFIG`'s own canonical key order (`cogmap`, then `seyu`) and filter down to accessible ones, so "first" means the same thing everywhere in this app (matching, for example, `/admin/users`'s own column order) regardless of grant history. Verified via new unit tests asserting canonical order survives a reversed-insertion `orgAccess` object, and that every `resolveLoginDestination` scenario with ≥1 accessible brand returns the correct per-brand Forecast URL.

**Sign-in prompt on the root landing page (2.4.76).** Owner-requested: `app/page.tsx` (the plain marketing page, `AI Sales Lead Collector` / contact info / `InfoCard`) had no way to sign in at all — a first-time visitor who already had an account had to already know to open the hamburger. `app/page.tsx` converted from a Server to a Client Component (`'use client'`, `useAuth()`) specifically so the prompt can be conditional: `!loading && !user` shows a `Divider` + "Already have an account?" + a `Sign in` button (the same `login()` from `AuthProvider` the nav's own Sign In link calls) below the existing general-information content; an already-logged-in visitor sees the same marketing content with no redundant prompt. Converting to a genuine Client Component resolves it as a byproduct — `curl http://localhost:3000/` now returns `200` in dev where it previously `500`'d.

### Input Validation
- POST, PUT, and PATCH payloads are all validated before processing (`validateLeadPayload`, with `{ partial: true }` for `PUT`'s partial updates; `validatePatchPayload` for action-envelope `PATCH`es)
- Brand-aware field normalization prevents cross-tenant writes
- Schema mapper/validator blocks forbidden cross-brand vocabulary in free-text fields (e.g. `value_proposition`). The pro/con fields themselves stopped being brand-specific in 2.3.0 — there's nothing left to forbid cross-brand there, since every brand shares one generic field
- `size` is enum-checked against `Small`/`Medium`/`Large`/`Enterprise` when present (not required) — previously documented in this schema but never actually enforced, which let free text describing scope rather than size tier (e.g. "Pan-European league") get stored and displayed as if it were a valid value. Existing out-of-enum production documents are not retroactively fixed by this — the check only gates new writes
- `decision_maker_name`/`decision_maker_title`/`decision_maker_contact`/`contact_phone` (as of 2.4.32, issue #45): no longer recognized fields anywhere — a request that still sends them has those specific values silently ignored, not stored. Decision-maker status is set via `contacts[].isDecisionMaker` instead. Production data was migrated on 2026-07-24 via a temporary admin endpoint (515 documents, confirmed via a follow-up dry run finding nothing left to migrate) — see `lib/migrate-decision-maker.ts`'s header and issue #45 for the full record; `scripts/migrate-decision-maker-to-contacts.ts` remains available for any future environment that needs the same migration
